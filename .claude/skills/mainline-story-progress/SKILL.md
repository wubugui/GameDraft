# 主线故事进度 · 核对与更新

## 这份文档是什么，为什么要准

`主线故事进度.md` 是**已在游戏里落地的主线故事**的唯一梗概，用制作人口述的川话写成，只有故事。
策划模式（production-mode）进模式第一件事就是读它，拿它判断"这一拍接在哪、前面发生过什么、人物此刻
什么处境"。所以它写错一句，后面每一次做内容的判断都跟着偏；它写进了没落地的东西，agent 会以为那段已经
能玩。**准确 = 每一句都能在游戏数据里找到出处，且那份数据玩家真的走得到。**

写这份文档的规则是制作人 2026-09-02 定死的，原文在两处（内容一致）：
`FindingDogStory/CLAUDE.md` 的「主线故事进度文档」一节、本仓库 `production-mode` 技能第七节。
**开工前把那一节原文读一遍**——本技能是按那六条规则执行的操作手册，不替代它们。

## 什么时候写，什么时候只报

| 制作人说的 | 做什么 |
|---|---|
| "更新进度文档""核对落地进度，更新这个文件""把 X 那段写进去" | 全流程，落笔 |
| "核对一下进度文档""看看进度文档还对不对" | 全流程跑到第 5 步，**只汇报不落笔** |
| "把文档里的台词更新到最新""台词对一下游戏" | 这是制作人**点名改他的段落**。第 0–2 步照做，然后按下面「台词对齐」做 |
| 什么都没说，只是你刚做完一段主线内容 | 不碰、不提、不建议更新 |

## 工具

两件，都只读：

```bash
# 本技能的查询脚本（下文简写为 mp）
sh scripts/py.sh .cursor/skills/mainline-story-progress/scripts/mainline_progress.py <子命令>

# 叙事交叉引用：一条信号谁发谁听、一个状态怎么进来谁在看着
sh scripts/py.sh -m tools.narrative_xref "<信号>"
sh scripts/py.sh -m tools.narrative_xref --state 图id.状态id
```

| mp 子命令 | 回答什么 |
|---|---|
| `doc` | 文档在哪、最后写盘/提交时间、有没有未提交改动、换行是 CRLF 还是 LF |
| `chain` | 主图从 initialState 走下去的状态顺序、每个状态怎么进来；哪些状态没接进主链 |
| `starts ID` | 谁在启动这张对话图 / 这段过场，挂在哪个 NPC / 热点 / 区域上、带什么条件 |
| `text ID` | 按顺序打印对话图或过场的台词（分支、选项、给物品、发信号都标出来）。过场默认略掉镜头/移动/等待，要核位置关系加 `--all` |
| `flag NAME` | 谁在设这个标记：`has_item_x` → 谁给 x；`rule_<规矩id>_acquired` → 谁给这条规矩（含碎片、分层授予） |
| `changed --since TIME` / `--base REV` | 从基线到当前工作树，过场台词 / 对话台词 / 任务文案 / 主图 / 场景接线变了什么 |
| `check --snapshot PATH` | 落笔后自检：原有行一行没动、换行没变、新增行没有括号/问号/引号/id/路径/半角字符。制作人点名改原有段落时加 `--allow-replace`，改动行只列出不判错 |

所有命令在 GameDraft 仓库根目录跑，Bash 里前面加 `PYTHONIOENCODING=utf-8`。
过场不是单独文件，全在 `public/assets/data/cutscenes/index.json` 里；对话图一张一个文件在 `public/assets/dialogues/graphs/`。
要在中文里搜字符，用 Grep 工具，别用 Bash 的 `grep` 配中文字符集——按字节匹配会和中文标点撞，满屏假命中。

## 流程

### 0. 找到文档，读全文，留快照

`mp doc`。找不到就停下问制作人位置（不同机器盘符不同：见过 `E:\GameDev\FindingDogStory`、
`H:\FDStory\FindingDogStory`），拿到后用 `MAINLINE_PROGRESS_DOC=<路径>` 再跑。
读完整篇，记住每段在讲哪件事、结尾停在哪、口气什么样。

**把此刻的文档复制一份到 scratchpad 当快照**（`cp <文档> <scratchpad>/主线故事进度_开工快照.md`）。
这份文档不止你一个人在写——制作人、FindingDogStory 那边的会话都可能在你干活时往里加东西，
git 里的未提交改动也不一定是制作人的。自检时拿快照比，不拿 git HEAD 比。

### 1. 拿主链顺序

`mp chain`。段落顺序只跟"主链顺序"走。

- 从 initialState 走不到的状态（现在有 `s02_beishi`…`s12_chufa` 一串旧 Demo 状态）**不是已落地主线**，
  哪怕它们有标签、有任务、有对话挂着，也不写。
- 标 `⚑ 分叉` 的状态：主线在这里有多条路，写之前先问制作人写哪条（或都写），不自己挑。

### 2. 把每个状态追到它的内容源

对主链上每个状态，搞清"玩家在这一拍实际经历了什么"。从它的**进入方式**往回追，直到落到玩家看得见的东西：

1. **收到信号进来**：`narrative_xref "<信号>"` 看发送方。
   - 发送方是区域 / 热点 / 对话节点 / 过场 → 找到内容源了。
   - 信号是 `state:某图:某状态` 这种派生信号 → 发送方是另一张叙事图的状态，再看那张图"能让它发生的路"
     里的信号，继续追，直到落到区域 / 对话 / 过场。
2. **条件满足自动走**：条件是 `narrative` 叶就 `narrative_xref --state` 追那张图；条件是标记就 `mp flag` 查谁设
   （通常是某段对话里 `giveItem`）。制作人 2026-09-15 起要求编排优先用叙事状态机、少用 flag，
   所以同一拍过段时间可能从"标记齐了自动走"改成"收到信号走"——每次都按数据现状追，别凭上次的记忆。
3. **这一拍窗口里还有什么**：`narrative_xref --state 图.状态` 的「谁在看着这一拍」——哪些 NPC 在这一拍出现、
   哪些对话按这一拍分支。它们是这一拍里玩家能碰到的东西。
4. 拿到对话图 / 过场 id 后：
   - `mp starts <id>` 确认它**真的被启动**，看挂在谁身上、条件是哪一拍。
   - `mp text <id>` 读台词。区域 onEnter 里依次启动几段过场的，按启动顺序逐段读。
   - 场景进场时启动的对话（场景 `onEnter`），`starts` 也能查到。
   - 场景名看场景 JSON 里的 `name` 和从哪儿转场过去，别看 id：`test_room_b` 就是游戏里的"后巷"，崖墓任务发布挂在那儿。

### 3. 判定哪些算落地

写进文档的只能是玩家真能走到的。逐条过：

| 算落地 | 不算落地 |
|---|---|
| 主链必经路径上接了线的对话 / 过场 / 区域演出 | `starts` 查不到启动方的对话图、过场（文件在，但没接线） |
| 被 `starts` 查到的那几段过场拆分件 | 同名拆分件里没被启动的父件 / 兄弟件（`__part1` 接了线，父件和 `__part2` 就不算——台词常常不一样） |
| 这一拍窗口里接了线的 NPC 对话（非必经也算，写不写看第 7 步"可选互动"） | 过场里 `disabled` 的步、对话图里从 entry 走不到的节点（`text` 会标出来） |
| | 挂在拿不到的标记上的分支：`mp flag` 查不到任何来源，且按它的提示在 `src/` 也搜不到代码直接设（例：备上山的糯米 / 公鸡 / 桃木 / 草席要先得规矩，而数据里没有任何给这几条规矩或碎片的动作） |
| | `线外_`、`未接_`、`验证_` 开头的对话图和过场（线外 = 主线之外的零碎；未接 = 没接线；验证 = 验收用） |
| | 主链外的状态（第 1 步）；系统提示（弹地图、说明卡、三把火首现）；设计稿里有、数据里没有的一切 |

**占位内容**：台词是 `？？？？`、明显临时的句子（"吃了一包方便面"那类）——不照抄，按这一拍在流程里起的作用
一句带过（例：`主线_初上跑马梁` 只有一句 `？？？？` → 写"他上了跑马梁"）。
说话人显示成 `？？？` 不等于台词是占位，台词本身是真的就照常写，人物写成"来了个人""那人"。

### 4. 对齐：文档写到哪一拍了

把文档段落和第 2 步追出的内容源逐拍对上，找出**文档覆盖的最后一个状态**。之后的主链状态就是待写的。

要验多细：
- **文档覆盖的最后一拍**：`text` 全文读完，逐句和文档对（它最可能被后来的改动碰到，也是新段落要接的口气）。
- **更早的拍**：确认内容源还接着线（`starts`），再看第 5 步的变化清单；没出现在变化清单里的拍，算对得上，不用逐句重读。
  出现在变化清单里的拍，回到"逐句对"。

对不上的情况：
- 文档某段在数据里找不到 → 可能是那段内容被删了或改道了，记下来，第 5 步一起报。
- 数据里有一拍、文档跳过了 → 如果是在文档已覆盖的范围中间，不擅自往制作人段落中间补，报给制作人。
- **文档写得比游戏还远**（结尾有一大段在数据里找不到、主链上根本没有那几拍）→ 那不是落地内容，
  可能是制作人自己写的、也可能是别的会话按设计稿写进来的。**不删、不改、不在它后面续写**，
  这次新写的内容也不往它后面接；停下来把那段的起止句贴给制作人，问是不是他写的、要不要留。
  实例：2026-09-15 更新完"他上了跑马梁"二十分钟后，文档末尾多出一百多行跑马梁鬼打墙（带引号、问号、
  数据里没有的糙米），跑马梁在游戏里只有一句 `？？？？`。

### 5. 核对已有段落有没有被数据推翻

**找基线**（制作人上次写这份文档时的数据版本）：

- `mp doc` 看文档最后提交时间；文档如果有未提交改动，用 `git -C <文档所在仓库> log -3 -- 故事设计/主线故事进度.md` 找制作人那次提交的时间。
- 常见情况是写完文档后几分钟才把数据一起提交（09-11 20:15 写文档、20:18 才提交数据），这时一个时间点对应两个候选基线：
  "写文档之前最后一个提交"（宽）和"写文档后紧挨着的那个提交"（窄）。**两个都跑**：
  `mp changed --since "<写文档时间>"` 和 `mp changed --base <紧挨着的提交>`。
  两份清单都有的变化 → 确定是写文档之后改的。只在宽清单里有的变化 → 拿文档原文去对：文档写的是旧版就是
  后来改的，写的是新版就是写文档时已经有了。

**对每一处落在已覆盖拍里的变化，回数据核实，分四类**：

| 变化 | 处理 |
|---|---|
| 纯表现改动（换成过场、加镜头、并行轨、加动作气泡）且台词意思不变 | 不动文档。汇报里一句话带过 |
| 新增了可选互动，不改变这一拍发生了什么 | 不动文档。汇报里列出，说没往他的段落里补 |
| **制作人段落里当原话用的台词**（冒号后面的话、破折号后面的心里话）在游戏里改了词或没了 | 不改原文。汇报里贴出文档原句 + 游戏现在的台词，问他要不要换。这类最容易被当成"换词"放过——文档是在引他的原话，原话变了就得让他知道 |
| 事实变了：发生的事、结果、谁说的、钱数、人物去向、顺序 | 不改原文。汇报里贴出原句 + 现在数据里的样子，问制作人以哪个为准 |

只核对不写的，到这里写汇报（第 8 步格式）结束。

### 6. 定落笔位置

- 制作人指明了位置（"接在癞子那段后面"）→ 就放那儿。
- 他只说"更新"没指位置 → 位置就是故事推进到的地方，按主链顺序接。**默认接在文末。**
- 文档最后一段是一句收束（比如"他一个人摸黑上山去了。揣着那一文。"），而新落地的拍有一部分发生在
  这句之前（备家伙、出城前撞见谁）、一部分在它之后（出了城往哪走）——就把前一部分插在收束句那段**之前**，
  后一部分接在它**之后**，让顺序和主链一致。制作人的段落本身一个字节不动、不拆、不挪。
  （2026-09-15 第一次更新就是这样落的，制作人看过没提异议；汇报里必须写清插在哪两句之间。）
- 永远不往制作人的某一段**里面**加字，不改他的标点、不合并他的段落。
- 文档末尾有第 4 步说的"比游戏还远"的一段 → 先问，不往它后面接。

### 7. 写

**先对口气**：写之前重读文档里最近两三段。文体是制作人定的——川话梗概、贴身第三人称、短句、不解释、不抒情。

从数据到梗概的压法（全部照着文档里已有段落学来的）：

- **一拍一段**，段落短。一段里是这一拍发生了什么、他怎么应。
- **对白压成转述**：`谁 + 动词 + 冒号 + 话`，话尽量用台词原词，川话词汇照搬台词里的，不自己换成普通话，
  也不自己造台词里没有的川话。例：数据 `主角：老哥，借几样家伙。今黑了要上牛头梁梁，背个死人子下来。`
  → `他寻到打更的，借家伙：今黑了要上牛头梁梁，背个死人子下来。`
- **人物口头禅 / 心里话**可以直接当叙述用，前面加破折号：`——钱跑了又自己滚回来。老子今天运气凶得很。`
- **只写他感知到的**：数据里的伏笔、真相、系统提示（三把火、说明卡、地图解锁提示）不点破、不写成叙述。
  他没看出不对，文档就不写有什么不对。
- **不补数据里没有的东西**：动作、表情、停顿、心理、天气、景物、语气副词，数据里没有就不写。
  反例：台词是 `半夜三更上那种地方……`，不许写成"打更的愣了一下"；主角第一句就开口借，也不必写成"开口就借"。
- **称呼**：文档里已经叫过的沿用（官爷、癞子、瞎子李、店小二、掌柜）；新人物用台词里别人怎么叫他、
  或场景里的显示名（打更的、巡夜的官差）；显示名是 `？？？`、`New NPC` 这类就写"来了个人""那人"。
- **数字、钱数、地名**照数据写（二百三、五百文、牛头梁梁、跑马梁、南门）。
- **选项分支**：几个选项殊途同归 → 只写汇合后的共同部分，必要时取最贴人物性格那条的一两句；
  选项导致这一拍结果不同 → 这是真分支，停下问制作人写哪条。
- **可选互动**（这一拍窗口里接了线、但不是必经的 NPC 对话）：有这一拍的味道、压成**一段两三个短句**写得完的，
  可以写；更长、或拿不准的不写，汇报里列出来让他定。写了的也在汇报里标明"这段玩家可以不碰"。
- **任务文案不是故事**：任务标题 / 描述 / 目标文字只拿来理解流程，不当台词写进文档
  （它们常写着"白天听来的规矩都想起来了"这种数据里并没有演出来的东西）。
- 文档里**不许出现**：括号注释、问号、引号、表格、列表、标题、状态 id、文件路径、半角字母数字、待办、"本段…"之类说明。

**怎么写盘**：落笔前**重读一遍文档**，和开工快照比一下有没有人刚改过（有就回第 4 步重新对齐）。
然后用 Edit 工具在定好的位置插入（`old_string` 带上前后一句做锚点）。不要用 Python / shell 重写整个文件——
Windows 上 Python 写文本会改换行、全文变 diff；Edit 工具会保持文档原来的换行（CRLF 还是 LF 以 `mp doc` 报的为准，
仓库里 git 存的和工作区里的可能不一样）。

### 8. 自检，然后汇报

**自检**（全做）：

1. `mp check --snapshot <开工快照>`：原有行删改为 0、换行没变、新增行违禁扫描干净。任何一项 ✗ 就撤回重来。
   新增行里如果有不是你写的（别人同时在改），先弄清是谁的，汇报里说明，别当成自己的交付。
2. 逐句对出处：新写的每一句，能在第 2 步的 `text` 输出里指出依据（哪段对话 / 过场的哪句、哪个接线动作）。指不出来的删掉。
3. 不提交 git——制作人没说提交就不提交。

**汇报**（给制作人看，他不看代码：用这一拍的叫法和人话，不贴状态 id、不贴文件路径、不贴命令输出）：

- **核对结果**：已有段落跟游戏对得上到哪儿；有哪些表现层改动（一句话带过）；原话被改的、事实被推翻的逐条贴原句 + 现状，问他。
- **新写了什么**：几段、各讲哪一拍、放在哪（插在哪两句之间 / 接在文末）；哪段是可选互动。
- **没写的和原因**：占位只写了一句的、拿不到所以不算落地的、可选互动没补的、系统提示。
- **要他拍板的**：分支写哪条、原话要不要换、事实冲突以哪个为准、来路不明的段落留不留。没有就不写这一项。
- 不建议"还可以补什么"。

## 台词对齐（制作人点名时才做）

制作人说"把台词更新到最新"，意思是文档里人物说的话要和游戏里现在的台词一致。他的段落这时可以动，但只动台词。

1. 按第 2 步把文档覆盖的每一拍的内容源全部 `text` 出来（过场按接线顺序逐段），存到 scratchpad 一份对照。
2. 逐段逐句找文档里的**台词**：冒号后面的话、破折号后面的心里话、"说……""喊……""骂……"后面转述的话、说书人讲的内容。
   叙述（动作、他怎么想、谁在哪）不是台词，不动。
3. 判断标准：**台词里用了游戏现在没有的说法，就换成游戏现在的原词。**
   - 文档是游戏台词的压缩（只取了其中几个词、省了语气词），词都在游戏里 → 不动。
   - 文档里的词游戏里没有（旧版台词、他凭记忆写的、换了说法）→ 换成游戏里对应那句的原词，句子骨架、前后叙述不变。
   - 文档没写的台词不补回来——他当初省掉是他的取舍。
   - 一句台词在游戏里整个没了、换成了意思不同的另一句 → 用新那句替换（例：心里话"钱跑了又自己滚回来"→"不如去翻盘"）。
   - 游戏台词明显是错字（"来和蹲一排"少了"你们"）→ 保留文档的写法，汇报里提一句。
4. 同样用 Edit 逐处替换，落笔前和快照比一次。
5. 自检用 `mp check --snapshot <快照> --allow-replace`：它会列出所有被改的原有行，逐行确认都是台词改动、没有顺手改叙述。
6. 汇报逐条列"原来 → 现在"，用人话说在哪一段；再列"游戏里有、文档没写"里值得他知道的新台词（只列，不补）。

## 判例

**2026-09-15，第一次按落地数据更新**（文档停在"他一个人摸黑上山去了。揣着那一文。"）

- `chain`：主链走到 `state_9 初到跑马梁`；文档覆盖到 `state_7 夜遇癞子·应下上山`。待写 state_8、state_9。
- state_7 → state_8 是"四样东西齐了自动走"。`flag has_item_torch` 等 → 全来自打更的那段对话（`序章_夜巡打更人_备上山`；
  火把另有 `线外_` 拉客女给，线外不算）。`--state` 看出这一拍窗口里还有两个巡夜官差（`序章_夜巡官差_宵禁`，按应没应下分两种回话）。
- 任务里还列了糯米 / 公鸡 / 桃木 / 草席和一句"还有几样没备齐"的独白——四条规矩数据里没有任何来源，不写。
- state_8 → state_9：南门外小路走到头 → 弹地图 → 进跑马梁场景启动 `主线_初上跑马梁`，台词是 `？？？？` → 占位，写"他上了跑马梁"。
- 核对：`路遇·钱自己回来了` 从对话图换成了三段过场，怪人的台词没变，加了开头结尾几句和三把火首现。
  **但**制作人段落里的心里话"——钱跑了又自己滚回来。老子今天运气凶得很。"是照旧对话原话写的，新过场里这句没了，

## 常见坑

- **文件在 ≠ 落地**。`序章_街巷_路遇私铸钱` 对话图还在仓库里，但区域已经改成放过场，它没人启动了。一律先 `starts`。
- **读错拆分件**。`主线_铜钱脱落滚走` 父件第一句是"这钱都用累了"，实际接线的 `__part1` 是"没得瘾儿，拽瞌睡了"。
- **场景的 `cutsceneIds` 清单不是接线**，只是预加载；`starts` 已经排除了它。
- **id 和标签会骗人**。场景 id（`test_room_b` 是后巷）、主图状态 label、任务标题、对话图 meta.title 都可能过时；以接线和台词为准。
- **设计稿会骗人**。`Demo制作资料/`、`故事设计/关二狗的故事.md`、配音稿与落地数据打架时以落地为准；
  配音稿只在一种情况下用：过场里一句台词没标说话人，查配音稿核归属。
- **判例不是答案**。判例记的是某一天的数据；数据会改（尤其 flag 正在往叙事状态机迁），每次都重新跑命令核。
- **跨仓库**。文档在 FindingDogStory 仓库，数据在 GameDraft 仓库，git 命令记得用 `-C` 指对仓库。
