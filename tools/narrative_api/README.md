# narrative_api —— 叙事图编程编排（设计中，尚未实现）

> **⚠ 这里的样例代码现在跑不了。**它们 `from narrative import ...`，而那个包还不存在。
> 样例是**目标接口的样子**，用来判断这个方向对不对，不是可执行代码。

## 这是什么

把叙事编排从「GUI 连线」改成「写程序」的一层。**产出不变**——仍然是
`public/assets/data/narrative_graphs.json` 那坨 JSON，运行时、校验器、编辑器**零改动**。

两半，缺一不可：

| | 干什么 |
|---|---|
| **叙事图构造 API** | 造机器/拍/边/绑定，产出 JSON。不变量以 `design/spec-v17.md` 为准 |
| **世界查询 API** | 只读地问世界："所有 inspect 热点""雾津街头的 NPC""所有规矩"。**规模化编排的前提**——不能遍历就只能逐个点名 |

世界查询**不需要给数据加任何字段**：实体已经有唯一 id，缺的只是「能问」。
地址是 `(场景, id)`——实测跨场景重名的有 NPC 16 / 热点 8 / zone 3（多为编辑器占位名未改，
以及 `exit_to_street` 这种语义上就该同名的），而现有数据里 zone 引用本就写成 `码头白天:new_zone_2`。
单 id 能唯一定位时可省场景，**歧义时 fail loud，不许挑一个**。

### 为什么

不是因为 GUI 表达不了——它表达得了。是因为**规模上去之后人管不过来**：

| | 项目里有多少 | 在叙事里存在的 |
|---|---|---|
| NPC | 111 | **6** |
| 热点 | 117（其中 inspect 73） | **5** |
| zone | 44 | 1 |

**世界里 95% 的东西叙事系统不知道它们存在**——因为每让一个实体参与叙事就要手画一张
wrapper 图。这不是"将来会麻烦"，是**已经因为麻烦而没做**。

想要的是把编程领域管理复杂度的那套东西（抽象、复用、模块化、diff、审查、静态检查、测试）
直接用上，而不是在 GUI 里一个一个重造。

### 边界（重要）

**不侵入现有实现。**这个文件夹自成一体：

- 不改 `src/`（运行时）
- 不改 `tools/editor/`（GUI 编辑器）——将来复用 `ProjectModel` 的话也是**引用**，不是改它
- 不改 `public/assets/data/**`（内容数据）
- GUI 编辑器照常用；手写的图和生成的图**共存**，靠 provenance 戳区分

## 两条硬约束（设计时就得满足，不是以后再说）

**① 确定性：同一份源必须产出逐字节相同的 JSON。**
否则每次 build 都是一堆无意义 diff，版本控制和审查失效——**而那正是这件事的主要收益之一**。
（Bazel 的 Starlark 把自己阉成受限方言就是为了这个。）

**② 每个 composition 的真源只能是「代码」或「GUI」二选一，禁止回流。**
生成的 JSON 不许再被 GUI 改回去——改了产物，下次 build 抹掉，是所有代码生成系统翻车的经典方式。
用 provenance 戳 + 编辑器只读闸门保证，不能只靠约定。

## 与现有系统的关系

- **产物**：`narrative_graphs.json`（以及模板盖章那几样：quests、对话桩）
- **语义模型**：`src/core/NarrativeStateManager.ts` 的运行时行为是权威，`design/spec-v17.md` 是它的语义提炼
- **世界查询的实现**：`ProjectModel` 数据面的**只读外观**——它本来就把场景/NPC/热点/zone/
  规矩/任务/对话全载进来了，不需要新的加载器
- **可能复用**：`tools/editor/project_model.py`（载入 / 脏桶 / 两阶段写盘 / 存盘前校验）、
  `tools/editor/shared/signal_refactor.py`（级联改名）、`tools/narrative_xref/`（引用扫描）
  —— 一旦编译期有了名字解析，xref 是副产品，那个包连同它的登记表可以退休
- **迁移方式**：**逐个 composition**。先挑一个改成生成，其余照旧 GUI 画。
  不满意就把生成的 JSON 留下、脚本删掉，回到原状。
