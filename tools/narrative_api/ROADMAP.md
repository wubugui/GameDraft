## P0 —— 必须先有，否则后面都写不出来

### 1. 形式语义（spec 唯一剩下的悬案）

求值策略目前只活在 `src/core/NarrativeStateManager.ts` 里：
每次扫描每图至多选一条转移、状态变化后重扫至不动点、队列与嵌套排空、订阅执行时机、
priority 降序 → 平级取声明序。

**§5 那七条静态检查全部建在它上面**，不写清楚就无法定义"这个检查在检查什么"。

### 2. 符号表生成器（`W.*`）

扫 `public/assets/**` 生成类型化引用模块。覆盖：场景实体（NPC/热点/zone）、对话、
小游戏、过场、任务、规矩、信号、flag、位面、现有叙事机器及其拍。

要点：
- 生成**类型化引用对象**（`NpcRef`/`HotspotRef`/…），不是 `str` 常量——否则只挡住"值错了"，挡不住"类型错了"
- 符号路径带场景，消解跨场景重名
- id 非法标识符时按**单射**规则清洗，两个 id 洗成同一个符号就**生成失败**，绝不静默合并
- 生成物**入库**：世界里加了个 NPC 会以 diff 形式出现，是审查信号
- 新鲜度三条：generate-then-build / 数据指纹对不上就 fail / 生成物入库

**这一项可以先于其它任何东西做，而且自己就能用**——现在手填实体 id 的地方（`dev_narrative_warps.json` 之类）立刻受益。

### 3. 世界查询面（`world.*`）

`ProjectModel` 数据面的**只读外观**。它本来就把场景/NPC/热点/zone/规矩/任务/对话全载进来了，
不需要新加载器。查询返回类型化引用（与符号表同一套类型）。

## P1 —— 主体

### 4. 叙事图对象模型

把 `model.narrative_graphs` 从裸 dict 包成有不变量的对象。
`design/spec-v17.md` 的 §1/§2 落在这里，§4 的 17 条排除 = **API 上没有这些方法**
（没有 `emit()` / `setPlane()` / `setFlag()` / `createInstance()` / `freeze()`）。

### 5. 往返保真闸门 ⚠ 这条是生死线

**载入 → 一个字节不改 → 保存，输出必须与输入逐字节相同。**

风险具体：JSON 里有对象模型不认识的字段（`meta.editor`、`x`/`y`、将来别人加的），
对象只要读进来时丢了，save 就把它们抹了。
项目里已有四个同形状的测试可照抄：`test_canvas_roundtrip_safety` /
`test_condition_expr_roundtrip` / `test_cutscene_roundtrip_fidelity` / `test_paper_craft_roundtrip`。

### 6. 确定性

同一份源必须产出**逐字节相同**的 JSON。否则每次 build 都是一堆无意义 diff，
版本控制与审查失效——**而那正是这件事的主要收益之一**。
（Bazel 的 Starlark 把自己阉成受限方言就是为了这个。）

### 7. 生成物与手写物的隔离

每个 composition 的真源只能是「代码」或「GUI」二选一，**禁止回流**。
生成的 JSON 不许被 GUI 改回去——改了产物，下次 build 抹掉，是所有代码生成系统翻车的经典方式。
`attach_stamp_provenance`（`narrative_templates.py`）已有一半：来源+版本戳。
缺的是编辑器侧的**只读闸门**，得是硬闸门不是约定。

### 8. Qt 解耦（工程摩擦）

`ProjectModel` 依赖 PySide6 的 `QObject`/`Signal`/`QUndoStack`（没有 widget）。
无头跑脚本要么带 PySide6 + offscreen，要么把这三样解耦。不是拦路虎，但会天天硌脚——
尤其要在 CI 或 AI 脚本里驱动它的时候。

## P2 —— 有了主体之后

### 9. 静态检查七条

悬垂信号 · 不可达状态 · 死锁 · 振荡（反应式环）· 待接线（`todo`，与悬垂**严格分开**）·
`count` 目标非 `Done` · 维度拼写。

其中两条**现在就能命中真 bug**：`quest_return_ring.completed` 不可达、
`scenario_听书:kicked_out` 广播了没人听。

⚠ 必须跑得动上万台机器——线性/近线性，不能是指数的。API 让人一口气生成一万台，
而那是一万个没人审过的东西。

### 10. `narrative_xref` 退休

编译期有了名字解析之后，"谁引用了 X" 是解析表的反向索引，不是一个功能。
那个包连同它的登记表（`sources.py`）可以退休——本次会话里气泡台词整条通道在登记表里缺席、
答案静默少一截，就是登记表这种东西的固有病。

### 11. 首个真实迁移

**逐个 composition**。先挑一个改成生成，其余照旧 GUI 画。
不满意就把生成的 JSON 留下、脚本删掉，回到原状。
候选：那 16 台同构的一次性事件（形状最统一、风险最低）。

## 待定（需要拍板，不是技术问题）

1. **生成是编译期还是运行期** —— 读你的话是编译期（build 时跑，产物入库可看不可改）。运行期改图会毁掉存档与静态分析。
2. **手写那一半保持 GUI 还是也走 API** —— 倾向保持 GUI：画一张图很直观，没必要动。
3. **文本记号（spec §3）还要不要** —— 倾向不要。API 严格更强，两套表面要保持同义，维护成本还不回来。
4. **哪个规模化场景先做真实对照** —— S4 横切规则最能说明问题（GUI 结构上装不下），S1 背尸围观最贴玩法。

## 已经作废的方向（别回头）

| 方向 | 为什么废 |
|---|---|
| 做一门外部 DSL（自己的语法/解析器/LSP） | 作者是你和 AI，不是不写代码的人；宿主语言的抽象、工具、类型系统全是白送的 |
| `machine T(…)` 模板构造 | 有了函数，模板就是个返回机器的函数；"卫生"在函数里叫局部变量 |
| `active when C`（机器级冻结） | 挂起是实例模型的产物，本语言没有实例，问题从源头不存在 |
| 隐藏 id + 名字→id 映射表 | 作者写的就是 id；改名是全项目级联重构，存档兼容归存档系统 |
| 语言里管存档迁移（`migrations`） | 越界。正确改名级联完就没旧 id 了；存档那边本来就有版本号 |
| 发明"视图"这个概念 | 就是 find-references + lint + 测试；编译之后 xref 是副产品 |
