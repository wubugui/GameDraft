## 0. 一页结论

**目标模型**：一条规矩的每一层各是一张叙事小图（`graphId = <ruleId>__<layer>`）。
**`reached` = 掌握了这一层**（单调只增，知识不会遗忘）；**`active` = 现在信的是哪一版**（可来回改，正好是"验证状态会变"）。
掌握与可信度分走 NarrativeStateManager 已有的两种语义，**零新引擎能力**。

**代价**：4 个 L2 原语（1 条件叶 + 1 action + 1 数据字段 + 1 生成器 CLI）、1 个 L3（累积细化的修订表）、以及 3 件必须先修的存量问题。
**净代码是减的**：删掉 3 个旧 action、9 条 flag pattern、EncounterManager 的 5 处直读、`rule_used_*` 死键。

**三条不选也得认的事实**（三方案独立得出、对抗组核实通过）：
1. 位面在物理上装不下规矩状态
2. 20 条规矩超出 demo 期产能，应降到 6~9 条
3. "打出知识"这条主玩法通路**从未在正式内容里跑过**，是零基线重建而非搬运

## 1. 对两条约束的技术反馈

### 1.1 「规矩状态完全接入位面系统」——这一半做不到，我建议改口径

| 事实 | 证据 |
|---|---|
| 位面存不了任何东西 | `PlaneReconciler.serialize()` 恒返回 `{}`；`deserialize()` 只清 manual override 后从叙事状态重派生（`src/systems/PlaneReconciler.ts:407-419`） |
| 位面是全局单激活标量 | `activePlaneId`（`:93`）；同时激活的点名 >1 个不同 planeId 才 `console.error`（`:467-486`） |
| 规矩是可累积可并存永久的 | 玩家同时掌握 20 条；`extends` 是单继承（`plane/types.ts:62`），N 条规矩组合需要 2^N 条手写位面 |
| 位面标注成本按实体数×位面数增长 | 一个背尸位面在两张场景产生 **30 条** `planes` 标注，其中 **23 条**是纯记账式的 `["normal"]` 排他标注 |

四种可能解读的逐条判定：

- **(a) 学会某规矩 → 进入某位面**：只有当它表达一段**有始有终的行为期**才成立，那时它是"术"不是"掌握"。做成永久知识指示器 = 第二条同类规矩无处安放 + 与背尸位面互相顶掉（后进者胜）。**滥用。**
- **(b) 用位面的实体归属实现"象开入口"**：**明确滥用。** 实体的 `planes` 是静态 id 白名单（`SceneManager.ts:263-268`），零条件表达力。正解早就存在且零新增：`conditionHidesEntity:true` + `conditions:[{rule:…}]`，全项目已有 268 处 narrative 条件叶在用同款语法。
- **(c) 术 = 切位面**：四种里最贴既定语义，但覆盖面极窄。仅当术是**持续态**、位面是 archetype 级可复用、且经"状态点名"而非 `activatePlane` 直切时成立（命令式直切是 2026-07-05 明文否决过的）。撒米/贴符/喊名/摆位这些单发术**绝不该造位面**。
- **(d) 位面 = 事的执行期舞台，规矩改它的入口条件 / 参数档 / 结局分支**：**✅ 采用。** 这就是你自己那句话的后半段。

**D1 拍板（2026-07-26）：位面与规矩之间不建立任何系统级绑定。**

> 制作人原话：「设计规矩要灵活，自由按需应用位面等各种游戏现有机制，不是让你机械地认为位面死绑规矩。」

所以本计划**不定义任何"规矩→位面"的固定规则**。位面只是策划工具箱里的一件工具，和气味、三把火、小游戏、档案并列——**哪桩事要用、怎么用，编排时现场决定**。

系统这边只保证两件事，两件都是现成的：
- 位面由叙事状态点名进入 → 规矩状态能决定事件图走不走得到那个点名状态（**入口天然可控**）
- `{plane:…}` 条件叶已在统一条件工厂注入 → 规矩的可用性能感知当前世界态（**读天然可用**）

以及一条**可选**的现成手法（不是规则，是备选）：准备度可以分岔到 `extends` 派生的位面变体档（如 `背尸_生手` / `背尸` / `背尸_老手`，只覆盖 `healthDrainPerSec` 与 `speedScale`）——想用就用，不想用就不用。

**唯一的硬纪律**：规矩层图的任何状态**一律不得写 `activePlane`**（validator error）。层图是永久单调的，一旦点名位面就永远点着，会把别的位面顶掉或被顶掉。**规矩不产位面，位面由事件产。**

> 对抗组核实修正：方案1/3 声称"点名第二个位面就每次 scene:ready 都 console.error"——**误报**。只有同时激活的点名 >1 个不同 planeId 才 error，同图内互斥状态不会。真正会响的只有 `validateActivePlanes` 的逐声明 warning。**不要为这个不存在的问题改校验器。**

### 1.2 「禁止用 flag」——完全可行，耦合面比预想小一个量级

| 事实 | 证据 |
|---|---|
| RulesManager 对 FlagStore **只写不读** | 全文 6 处 `set`，零 `get`（`RulesManager.ts:222,251,252,256,260,265,272`） |
| 真相源只有两个集合 | `acquiredFragments: Set` + `grantedLayers: Map`（`:83-89`）。flag 全是派生投影 |
| 内容侧读规矩 flag 只有 **2 处** | `archive/books.json:85`、`encounters.json:75`，都是 `rule_rule_*_acquired` |
| 代码侧读规矩 flag 只有 **1 处** | `EncounterManager.ts:120,121,127,153,154`（一次读 5 类键，绕过 RulesManager 直读 FlagStore） |
| 要清的 flag 共 6 类 + 11 处登记 | `fragment_*_acquired` / `rule_*_fragments_collected` / `_total` / `rule_*_<layer>_done` / `rule_*_acquired` / `rule_*_discovered`；`flag_registry.json` 9 条 pattern（`:324-384`）+ **2 条被错误钉成 static 的派生键**（`:208`、`:212`） |

**迁移形状（三方案完全一致，直接采纳）**：`RulesManager` 从"状态所有者"降级为**"叙事状态的只读投影 + 定义表"**，`serialize()` 返回 `{}`（与 PlaneReconciler 同型），订阅 `narrative:stateChanged` 后**继续发出既有的 4 类事件**（`rule:acquired` / `rule:layer` / `rule:fragment` / `notification:show`）——**AudioManager 与 NotificationUI 一行不改**。换后端不换事件契约。

## 2. 目标模型

### 2.1 拓扑：一层一图

```
graphId = <ruleId>__<layer>          例：rule_dry_corpse_walks__li
states  = 未闻(initial) → 未验 → {验成 | 存疑 | 推翻 | 细化_排除墨线 | …}
```

- **`reached('未验')` = 掌握了这一层**。单调只增，正好等于"知识一旦学到就永远有"。
- **`active` = 当前信的是哪一版**。可来回改（含降级），正好等于"敢不敢信"这条会变的轴。
- 三层**互相独立、无结构依赖**——`hasLayerImpl` 现有语义就是扁平 OR（`RulesManager.ts:126-136`），拿到 shu 不要求先有 xiang。

**为什么必须一层一图**（对抗组三个视角一致）：
- 单链模型（unknown→xiang→li→shu）物理上无法表达"回头验证已越过的层"——一张图只有一个 active，推进到 shu 后 `li_ok` 永远不可达。而设计稿的核心场景恰恰是"先从书上学全三层（未验证），再在事里逐层验证/推翻"。
- 严格单向阶梯直接杀掉设计稿的招牌伏笔：**⑤ 码头古籍给 R3 的『理』，R3 的『象』要到 ⑦/⑨ 才给**。跳级授予在阶梯模型里是**静默 no-op**，零日志零校验。
- 也杀掉"**有些**术只有理能指向"里的"有些"——`rule_zhenshi_sizhang`（R4 镇尸四样）现网就是 `{象, 术}` 无理。

### 2.2 owner 绑定：不绑

**层图不设 `ownerType`/`ownerId`，只靠 graphId 命名约定索引。**

理由（工程守门人核实）：一个 owner 挂 3 张 wrapper 是全项目首例（现网 multi-wrapper owner 数 = **0**）。`getPrimaryGraphByOwner` 对 >1 直接 `recordPrimaryOwnerAmbiguous` 返回 undefined（`NarrativeStateManager.ts:711-719`），连带 `@owner` token 全部失效，还要为规矩给 `validateOwnerBindings` 开一条**全局**豁免——那条护栏一旦让渡，将来别处误挂多 wrapper 不再有人提醒。

规矩不需要 `@owner` token，实测零损失。**这条比"加 ownerType='rule'"省一整套同步（TS union / Python / web dist / 编辑器下拉）。**

### 2.3 组织形态：单 composition

全部规矩层图收进**一个** composition（`rule_ledger`），每张层图是一个 wrapperGraph 元素。

侧边栏"编排列表"只 **+1 项**而不是 +20~60 项。现网 `xungou_demo_main` 已带 70 个 elements，规模被验证过。**痛点从来不是图的数量，是手工画图。**

### 2.4 读法：一个 `rule` 条件叶

```json
{ "rule": "rule_dry_corpse_walks", "layer": "li", "mode": "usable" }
```

| mode | 语义 |
|---|---|
| `usable`（**默认**） | 已解锁 **且** 当前版本未被推翻 |
| `known` | 只问解锁，不问可信度（显式写才有） |
| `discovered` | 听说过（含未解锁） |

**`usable` 是唯一 safe-by-default 的设计。** 裸写 narrative 叶的方案要求每一处规矩门都手写 `all[reached:shu, not(reached:推翻)]`，而**没有任何校验能强制那个 not**——漏写一处的表现是"被推翻的规矩仍然开着入口"，只能靠玩测发现。这笔 L2 是值的。

底层 100% 走 NarrativeStateManager 查询，**不是第二真相源**。

### 2.5 写法：一个 `advanceRule` action

```json
{ "type": "advanceRule", "params": { "ruleId": "rule_dry_corpse_walks", "layer": "li", "to": "验成" } }
```

运行时翻译成规范信号。解锁一层 / 验成 / 存疑 / 推翻 / 细化 **全是同一个动作、同一个心智**。

**必须补的诊断（两个方案都漏了）**：`reportUnlistenedSignal` 有 `getListenedSignalKeys()` 短路（`NarrativeStateManager.ts:1599-1613`）——只要图里挂过这个 signal（哪怕 from 不匹配），连 warning 都不报。所以 `advanceRule` 的 handler 必须自查：
- 目标版本在该层图不存在 → `reportDevError`
- 存在但当前 active 无出边 → `recordIssue(warning)` + dev 报错面

**不做这条，"授予了但没生效"在运行时完全不可见。**

**生成器纪律**：从**所有**状态（含 `未闻`）向每个目标版本连边；缺前置时自动补"先落 未验 再跳目标"。**禁止任何静默 no-op。**

### 2.6 层图是 rules.json 的派生物

策划**永远不进叙事画布编规矩**。层图由生成器从 `rules.json` 幂等产出。

**三个入口要求**（缺一即方案失效）：
1. RuleEditor 一个「同步层图」按钮
2. **`./dev.sh sync-rule-graphs` CLI** —— 保住"AI 直接改 JSON、agent 能自行跑通收尾校验"这条项目工作流
3. validator 漂移检查报 error，但**错误文案必须直接给出 CLI 命令**

**绝不挂进 `save_all`**（`project_model.py:706-790`）：那会让"rules 脏"强制带上"narrative_graphs 脏"，任何一张无关叙事图的历史 error 都会连带拦住纯 rules.json 的保存。

**也不用模板盖章**：`stamp_template` 的 comp id 碰撞是 error（`narrative_templates.py:589`），产物粒度是整个 composition，**撑不住 rules.json 演化**（现网 12 条规矩里 5 条只有 1~2 层，必然会长层）。

### 2.7 reactive 是局部手段，不是默认

方案1 的洞察值得保留：**规矩图读世界里已存在的叙事状态，编事件的人不需要知道项目里有哪些规矩**——这能把每桩事的编辑处数从 12~15 压到 5~7。

但**不能做全局默认**：
- 现网只有 **4 条** reactive；全量 reactive 化是 60~120 条，**15~30 倍跃迁**
- `MAX_DRAIN_STEPS=128`，失败模式是 `rejectQueuedItems` **整批丢弃**（不是降级）
- 更要命的是**级联**：玩家先满足术的条件（读了手札）、后满足象的条件（李天狗提一嘴），那一刻会在**同一次排空**里连跳三档、三条通知同时弹——"半懂→亲历→通透"的学习弧当场作废，而象理术的全部戏剧性正来自这条弧

**纪律**：默认 `advanceRule` 信号推（可诊断、可反查、零 drain 成本）；只在少数"跨十拍伏笔"场景用 reactive（如 ⑤ 古籍 → ⑨ 柴棚），且 **reactive 只允许做"补齐到 未验"这类单调补齐，禁止 reactive 改版本**——否则验证态会自己跳，玩家会认为系统在替他做判断，直接违反玩法铁律。全项目规矩图 reactive 总数上限写进 validator（≤20 条）。

## 3. 逐项改动 · L0~L3 分级

**分级定义**：
- **L0** — 不用改任何东西，现有能力直接够

- **L2** — 单点能力原语（新 action / 新条件叶 / 新参数 / 新 ownerType），走三件套登记
- **L3** — 系统级（新子系统、改存档结构、改核心模型、引入新构建纪律）

## 5. 两个盲区（原本是三个，D5 已解掉）

### 5.1 ~~「盲试」没有载体~~ —— **已解决，且省掉一个 L2**

> **2026-07-26 制作人纠正：我把锁二理解反了。**
>
> 不可逆的是**事件本身**，不是"甩规矩"这个动作。
> - **玩家随便试规矩是允许的、甚至是好事**——试了反而能验证一些东西，这正是"验证状态会变"的燃料。**不给"打出规矩"加惩罚、加冷却、加成本。**
> - **代价来自事件**：这桩事朝那个方向走了就回不去。事件是一次性的、有后果的，事件本身就是代价。
> - 锁二**不是防穷举的系统机制**，是编排事实：你不敢乱试，是因为你只有这一桩事可以拿来试。
> - 具体怎么判定、试错怎么恶化，**全由每桩事自己编排**——事件被触发时它当然知道自己该检测什么。

**结论**：不需要物品/库存条件叶，不需要用物动作，**不需要 flag 镜像**。原计划里那个待定的 L2 直接取消。
`RuleUseUI` 只列作者登记槽位的现状也不再是问题——策划在哪桩事登记哪些槽（含**错误答案槽**），就是编排本身。

### 5.2 ~~六种代价里五种无载体~~ —— **D7 已拍板：不做任何抽象**

> 制作人 2026-07-26：「时辰、天、名声、人情、机会窗口、留痕，都不需要单独抽象，全部都是策划的编排设计。」

**结论：零新系统、零新抽象。** 这些不是"待建的载体"，它们本来就该长在编排里。

具体怎么落（全部是现成的，与规矩状态同一套口径）：

| 代价 | 怎么记 |
|---|---|
| **钱 / 阳火 / 天** | 已有真载体：`giveCurrency`·`removeCurrency` / `decHealth`·死亡系绳 / `DayManager` |
| **名声 / 人情 / 机会窗口 / 留痕 / 时辰** | **叙事状态**——需要记账就给它一张 wrapper 图（如 `婆子家_口碑`：好 / 一般 / 记恨），要读就用 `narrative` 条件叶。要不要记、记多细，**逐桩事现场决定** |

**唯一的纪律（与第 1 条约束同源）**：**别为了记"名声−1""欠了谁一个人情"去开全局 flag。** 代价状态和规矩状态走同一条路——叙事状态机。这与项目既有工作法一致：*"进度走信号，flag 只在 state 的 `onEnterActions` 派生暴露，跨线依赖用 `narrative` 叶查任意图状态，不堆全局 flag"*（`agent_docs/content/methods/narrative-flow-authoring.md`）。

**至此全部盲区清空，本计划无待决项。**

### 5.3 ~~三方校验的权威归属~~ —— **D6 已拍板：选 A**

### 施工中发现并修掉的一个真 bug（越级授予）
