## 0. 一句话

把现在**各自为政的三套明暗**（角色吃烘焙 probe、背景吃原画、实体阴影吃全局 lightEnv）
合并成**一套实时光照**，结构是**两层**（§1.5）：

- **relighting 层（场景专属）**：把原画换成当前时刻的自然光；
- **氛围层（场景与角色共享）**：灯、雾、环境光——**算一次两边吃**，
  角色再乘上取自场景 3D 几何的 sky 遮蔽。

**"场景与角色完美融合"由此结构保证**，而不是靠角色去 gather 场景（那只是可选加分）。
光全部实时可变，只把跟几何走的量（法线、天穹可见性、命中图）预计算成场。

### 1.2 由 R1–R10 推出的系统需求

- **S1 光源成为一等数据**：天光 / 平行光（日月）/ **点光 / 聚光 / 面光**（R13），

- **S5 单一 shader 真相源**：光照合成数学只写一份 GLSL，游戏与工具预览共用

- **S6 连续性**：所有光照量能按时刻/天气连续插值（H3 无缝模式的直接要求）。
- **S7 逐灯可见度是阴影的唯一汇聚点**：场景阴影与角色阴影都只写 `vis_L`，

- **S8 阴影来源必须可显式声明**：角色阴影的方向/强度来自**被指定的**灯（真实或虚拟），
  系统不得自行推断（R8）。
- **S9 烘的是传输不是辐射**：probe 存 PRT 传输项，与光无关，光变零重烘（R9，展开见 §1.5）。

### ★ 1.35 灯光类型与效率架构（R13，制作人 2026-08-20 定）

**要求：点光 / 聚光 / 面光，全部实时高效。**（平行光另算，日月用）

#### 三种灯的实现

| 类型 | 着色 | 说明 |
|---|---|---|
| **点光** | `N·L/r² × 衰减 × vis_L` | 最便宜 |
| **聚光** | 点光 × `smoothstep(cosOuter, cosInner, dot(-L, spotDir))` | 加一个锥体因子 |
| **面光（矩形）** | **解析解，零采样** | 见下 |

★ **面光不用采样法**：本项目 Lambert-only（推导 §16.3 定：不重建 specular），
而**多边形面光对 Lambert 有闭式解**（Lambert 1760）：

```
E = (1/2π) Σ_边 acos(p_i·p_j) × (normalize(p_i × p_j) · N)
```

`p_i` = 面光顶点投影到着色点单位球的方向。矩形 = 4 条边 = 4 次 `acos`，
约为点光的 2–3 倍开销，**精确、零噪点、零采样**。
⇒ **不需要 LTC**（那是为 GGX 高光准备的，我们不做高光）。

★ **面光特别契合本项目画风**：亮窗、门洞、纸灯笼本来就是矩形；
面光朝向可**从深度场在该点的法线自动取**，贴到窗户位置朝向就自动对，不用手转。

#### ★★ 效率的关键不在灯的公式，在静态/动态分离

**场景是静态的，灯大多也是静态的** ⇒ 场景光照结果**缓存进 RT，只在参数变化时重算**：

| 触发重算 | 频率 |
|---|---|
| 时刻推进 | 离散事件，几秒一次 |
| 灯开关 / 剧情改灯 | 罕见 |
| F2 调参 | 编辑时 |
| **稳态** | **每帧零光照计算，只有一次纹理采样** |

灯分 **静态**（进缓存，零帧成本）与 **动态**（闪烁烛火、玩家手持灯笼 → 逐帧算）。

⚠ **这不是烘焙**：运行时算、参数一变就重算，不违反 R1。文档措辞须区分"缓存"与"烘焙"。

角色侧每帧都要算（它在动），但角色像素少（几千），且氛围光只是采样几个场、灯是解析式，便宜。

#### GTX 970 预算（估算，实现后须实测校准）

- **无阴影的灯**：约 20–40 ALU/盏，配合作用半径的屏幕包围盒剔除 ⇒ **几十盏无压力**
- **带阴影的灯**：每盏需沿深度场 march（24–32 步），半分辨率约 16M taps/盏
  ⇒ **同屏 4–6 盏是预算线**
- **带阴影的面光** ≈ 2–4 盏带阴影点光（软阴影取 2–4 个采样点）

⇒ R2「每盏灯独立开阴影」**就是预算闸门**。编辑器须显示「当前带影灯数 N/预算」，
不能等跑起来掉帧才发现。

#### 数据模型（草案）

```
Light {
  id, type: point | spot | area | directional
  pos: [x,y,z]              ← 伪世界空间（铁律 S12）
  color / intensity / kelvin
  range                     ← 作用半径，用于屏幕包围盒剔除
  spot:  dir, innerAngle, outerAngle
  area:  size[w,h], orientation（可从深度场法线自动取）, twoSided
  castShadow: bool          ← R2，也是预算闸门
  shadowSamples             ← 面光软阴影用
  dynamic: bool             ← 缺省 false 进缓存；闪烁/移动的标 true
}
```

### 1.4 阴影架构（R6–R8 展开）

**两类阴影的本质差别**：场景是**高度场**（有深度、可 march），角色是**立在伪世界里的片**
（没有体积，无法 march）。因此产生方式必然不同：

| | 场景阴影 | 角色阴影 |
|---|---|---|
| 遮挡体 | 深度场（可见壳） | sprite 的 alpha 剪影 |
| 算法 | 沿光方向 **screen-space heightfield ray-march**（物理） | **剪影平行四边形投影**（现有 `PlanarEntityShadow` 的办法，保留） |
| 光源 | 场景里的真实灯 | **手动绑定**的真实灯 或 **虚拟灯**（R8） |

**"resolve 到一起"的具体机制**：两者不再是"各画各的"，而是共同写进**逐灯可见度**
`vis_L(x) ∈ [0,1]`，光照合成时统一消费：

```
vis_L(x) = vis_scene_L(x) × vis_char_L(x)          ← 同一盏灯的两个遮挡源相乘
L_total  = Σ_L  light_L · vis_L · N·L / r²  +  skyColor · skyVis
```

这样解决三件当前做不到的事：
1. **影子与光自洽**——现在 planar 阴影是画在 `shadowLayer` 上直接叠暗色的 Mesh，
   **不参与光照计算**：灯更亮时影子不会更深。统一后"影子 = 这盏灯照不到"，天然自洽。
2. **影子不会叠黑**——同一盏灯的两个遮挡源**相乘**（都挡住 = 这盏灯照不到，到此为止），
   而不是两层暗色相加超黑。
3. **角色影子自动被场景几何裁切**（现有的碰撞 march + 前景 blend 继续生效）。

⚠ 与 `entity-lighting` 硬契约②"遮挡代理与着色代理禁止合并"**不冲突**：
这里合并的是**阴影的两个来源**，不是"遮挡代理"与"着色代理"。那两个代理仍分开（见 T8）。

### ★★ 1.5 光照结构（制作人 2026-08-20 定稿，本系统的骨架）

**场景光照分两部分，角色只共享第二部分。**

#### 第一部分：relighting（**场景专属**）

把原画从"白天的光"换成**当前时刻的自然光**——天光 + 日/月光 + 各自的遮蔽与投影
（方法见 §1.6）。

这一层**只有场景需要**：它干的事是"把画里烤死的白天光拆掉、换上此刻的自然光"。
**角色贴图本来就是 albedo，没有要拆的光**（推导 §4.1）。

#### 第二部分：环境氛围光照（**场景与角色共享**）

灯、雾、整体环境氛围。**算一次，场景和角色吃同一份。**

#### 角色的光照链

```
角色 = albedo × [ 氛围环境光 × sky遮蔽(取自场景 3D 几何)   ← ① 决定"该多暗"
                + 氛围光照(灯、雾)                          ← ② 与场景同一份
                + GI(可选：以 relit 场景为源 gather) ]       ← ③ 加分项
```

1. **sky 遮蔽**：从场景 3D 几何取该位置的天穹可见性 → 站巷子里就暗、站空地就亮。
2. **氛围光照**：与场景**同一份**参数、同一套灯与雾的数学。
3. **GI**：可选。

#### ★ "完美融合"的机制

**不是靠角色去 gather 场景，而是靠两者消费同一份氛围参数、同一个遮蔽场。**
这是**结构性保证**，不依赖 gather 的精度。

⚠ **本条纠正了本文档上一稿的错误**：上一稿把 gather 当成角色受光的**主力**
（"GI = 角色被 relit 场景照亮"），摆放错了。
gather 是**可选加分项**；承重的是「共享氛围光 × sky 遮蔽」。

#### 附带：这也把亮度问题解决得更干净

角色的主要受光**不来自那张暗的 relit 图**，而来自**显式的氛围光参数**
——想多亮给多亮，不受 LDR 动态范围限制（§1.5 致命前提那一节的问题因此大幅缓解，
但"gather 源必须是线性 HDR"对可选的第 ③ 项仍然成立）。

#### ★★ 致命前提：gather 的源必须是**线性 HDR 辐射场**，不是 relight 的显示成品

制作人 2026-08-20 指出"relight 之后亮度根本不够，拿去照角色等于没照"。**实测坐实**
（雾津街头夜，当前已导出的 `background_relight_夜.png`）：

| 量 | 当前 LDR 成品 | 说明 |
|---|---|---|
| 线性辐射中位 | 0.0036 | |
| **全图线性辐射最大** | **0.061** | ← 全图最亮的像素也才 0.06 |
| 动态范围（max/中位） | **17×** | 真实夜景里一盏灯笼是地面的几十上百倍 |

⇒ 拿它 gather，角色最多收到 0.06，**当然等于没照**。

**根因不是 gather 错，是烘的时候就把动态范围毁了**：`ev`、`ratio_max` 的 clamp、
以及最后压成 8bit sRGB，三件事把辐射场压进了显示区间。
**显示变换被烤进了辐射里——层次搞错了。**

##### 修法三件套

1. **relight 产出线性 HDR**（float，无 `ev`、无 clamp、不落 8bit）——这才是辐射场。
2. **灯按物理尺度给强度**：夜间天光/月光量级 0.01–0.02，一盏灯笼 50 ⇒ 相差几千倍。
   **亮度来自光源参数，不来自那张画**。画只提供反射率。
3. **显示变换（雾 → 曝光 → tonemap → 调色）移到最后**，**同时作用于背景与角色**。
   这是"两者永远一致"的结构性保证，不再依赖 β 那种事后补偿。

```
原画 ─[线性化]→ ─[÷ S_day]→ 反射率场
                                │
                     ─[× S_new(物理尺度：天光/月光/灯)]→ ★ 线性 HDR 辐射场
                                                            ├─→ [雾→曝光→tonemap→调色] → 画面
                                                            └─→ [probe gather] → 角色受光 ─┘(同一条显示变换)
```

##### 修法验证（同场景，加一盏强度 50 的灯）

| | 当前 LDR | HDR 辐射场 |
|---|---|---|
| 动态范围 | 17× | **692×** |
| 角色 E/π · 远离灯 | 0.0067 | 0.00051 |
| 角色 E/π · 灯旁 | 0.0067（**无差别**） | 0.042（**81 倍差**）|

共享显示曝光后：角色暗处 **4.2/255**、灯旁 **31.1/255**；背景中位 12/255、灯旁 88.5/255。
⇒ **角色终于会因为站在哪而明暗不同**，而当前实现是站哪都 ≈9/255。

##### ★★ 真 HDR：全局缩放不算，但信息也不可能全从画里挖出来（2026-08-20 实测）

制作人指出："简单地统一缩放那个图是不对的，要做真正的 HDR，哪些地方该亮哪些地方该暗。"
**对**——全局乘系数只是把一张扁平的图挪个位置，动态范围还是 17×。
但下面这轮实测证明：**缺失的动态范围信息，不可能可靠地从画里自动恢复。**

**试过并失败的方法：用反射率的物理上界当发光体探测器**
思路：`ρ = 原画 / S_day`，漫反射的 ρ 物理上不可能 > 0.9（新雪），超了就是发光体。
实测（码头白天 / 雾津街头，标定 p95=0.80）：过冲 3.4% / 3.3%。
**但被标出来的是栈道亮木板、白帆布、亮墙面——全是"被照得亮的漫反射面"，不是发光体。**
⇒ 正是 `2026-07-21` 决策「被否方案」里那条"纯统计亮度会把日景白石、亮路、水面抬成发光体"，
**本次完整复现，该结论继续成立**。

**试过并成功、但结论是"没什么可除"的方法：反推画里的日照方向**
判据：光除干净了，反射率就不该再与 `N·L` 相关（同一块木板朝光背光 albedo 应相同）。
在 (仰角×方位×强度) 网格上最小化 `|corr(log ρ, N·L)|`：

| 场景 | 不加太阳项 | 最优太阳项 | 反推结果 |
|---|---|---|---|
| 码头白天 | 0.094 | **0.000** | 仰角 50°、方位 220°、强度 0.3 |
| 雾津街头 | 0.132 | **0.001** | 仰角 50°、方位 180°、强度 0.8 |

方法有效（相关性归零），**但反推出的日照强度很低**——证明这两张原画本来就是**阴天漫射**，
没有强方向光可除。⇒ 那 3.4% 过冲不是"漏了太阳"，是**真的高反射率材质**。

##### ⇒ 结论：HDR 分两个来源，一个已知、一个人工

| 来源 | 怎么来 | 可靠性 |
|---|---|---|
| **我们摆的灯**（主要来源） | 强度是我们给的参数，想多亮给多亮 | **完全可靠**，与"手摆灯"既定方向一致 |
| **画里残留的亮块**（亮窗、水面高光） | **人工标**——工具里已有发光 mask 笔刷 | 可靠但要人工 |
| ~~从图像统计自动挖~~ | ~~反射率过冲 / 亮度阈值 / 肩线~~ | **已实测失败，勿再尝试** |

⇒ **不要试图从画里自动挖 HDR。**这既是实测结论，也让 R2/R4 两条复活风险彻底关闭。

##### 副产品：反推日照方向有独立价值（应入工具）

新加的月光/日光**方位角必须对齐画里烤死的日照方向**，否则新影子会和画里的旧影子打架。
现在有了可测的办法（上表的 decorrelation 搜索），不必再肉眼估。
⚠ 实测雾津街头是 **180°**，而我此前手填的是 **60°**——**当前预设里那个值很可能是错的**，
需按测量值复核。

##### 两条附带结论

- **变体 PNG 只能是显示产物，永远不能当 gather 源**。`tools/scene_relight` 现在导出的
  8bit PNG 用于预览与美术验收没问题，但运行时的辐射通路必须是 HDR buffer。
- ⚠ **需要一个全局标定常数**（新 unknown U11）：反解出的"反射率"是相对量
  （实测雾津街头中位 0.035），因为真实白天光的绝对尺度不可知。角色贴图的 albedo 却是
  另一套尺度。两者之间必须有**一个场景级标定常数**把尺度对齐，否则角色会系统性偏亮或偏暗。
  现有的 `beta`（角色曝光）实际上就是在事后补这个，新架构下它应变成**一个有物理含义的标定项**。

#### 关键工程问题与解法：probe 改存"命中几何"而非"积分结果"

现有 probe 缓存是对**静态**背景烘的**积分结果**（§3.2.2），背景一变即作废。解法：

- **离线**：每个 probe 沿 N 个方向在伪世界体素里 march，记录**命中了背景的哪个像素**
  （hit UV）或 miss（看到天）。这是**纯几何，与光无关，永不失效**。
- **运行时**：按 hit UV 采样**当前 relit 背景**，余弦加权求和 → E，投成 SH/bins 供角色着色。

| | 现在 | 改后 |
|---|---|---|
| probe 存什么 | 积分完的辐照度 E（`atlas_bin.bin` 860 KB） | 命中 UV + miss 标记（1680×64×RG16 ≈ **430 KB**，更小） |
| 光变了 | **必须全量重烘**（§3.2.3） | **零重烘** |
| 运行时更新代价 | — | 107K 次纹理采样 ≈ 0.1 MPix 一趟 pass；可逐帧，也可只在时刻/灯变化时更新 |

⚠ **这不是"屏幕空间积分"**（§5.1 的被否项 R1）：命中图是**离线在伪世界空间**算出来的，
深度分离在烘焙期就已完成，运行时只是按既定命中点取色。**此区别必须写进新决策卡**，
否则会被误判为翻案。

#### 双重记账规则（简化了，但仍必须守）

灯现在是一等数据、强度已知，所以**角色受灯的直接光走解析式** `N·L/r² × vis_L`，
**不能再从 gather 里重复收一次**。因此 gather 的源必须是"relit 场景**减去**解析灯的直接贡献"
——即现有 `base`/`emit` 分账的同一条规则（推导 §7.2）。

★ 但**大幅简化**：以前要靠 SAM3 语义分割去猜哪些像素是发光体；**现在灯是我们自己放的，
位置与强度全知道**。⇒ 发光体判定的整条不确定链路消失，同时消解风险 R2/R4
（"把 mask 当亮度阈值用"、"agent 猜灯位"）。

#### 角色光照的分量清单（R9，按承重顺序）

| # | 分量 | 做法 | 地位 |
|---|---|---|---|
| ① | **氛围环境光 × sky 遮蔽** | 天光色/强度（共享参数）× 该位置天穹可见性（几何场） | **承重**，决定角色"该多暗" |
| ② | **灯（与场景同一份）** | `N·L/r² × vis_L` 解析；法线用已有 `spriteNormalAtlas` | **承重** |
| ② | **雾（与场景同一份）** | 同一套 σ 与散射色，按角色自身深度 | **承重** |
| ③ | **GI（以 relit 场景为源）** | 命中图 gather（见下） | **可选加分** |
| — | **自遮挡 AO** | 现有 bulge/flatten 假法线那套 | 保留 |

⇒ **必须有一个天穹可见性场**（① 的乘子，角色位置采样）。这与场景 relight 用的
`sky_field` 是**同一个几何量**，只是一个逐像素、一个按角色位置采样——
**同源是"完美融合"的前半条保证**。

⇒ 命中图 gather 只服务于可选的 ③；②③ 都关掉时角色仍有正确的明暗结构。

### ★ 1.6 场景 relighting 的钦定方法（Q8 已答；**命名很重要，见末尾被否项**）

制作人 2026-08-20 验收的方法，按重要性排序是**三件事**：

1. **天穹可见性（逐像素半球 march 深度场）** ← 主承重件
   每个像素向上半球 12 个方向沿深度场 ray-march，算它能看见多少天空。
   巷道深处、屋檐下、墙根物理上收不到天光就是黑的；开阔街口、屋面就是亮的。
   实现：`tools/scene_relight/relight.py` `sky_field()`。
2. **定向光（日/月）投影** ← 第二承重件
   沿光方向 march 深度场得到真投影，方位角对齐原画烤死的日影方向。
   实现：`screen_shadow()` / `_march_blocked()`。
3. **先除掉白天光，再乘上新光** ← 只是最后一步算术
   `场景 = 原画 × clamp(S_new / S_day, 0, ratio_max)`，
   其中 **S_day 与 S_new 都由第 1、2 件构成**（天穹可见性 × 天光 + 定向光 × 投影）。

> **⚠ 这一步不是这个方法的名字。** 把它叫"比值法"会把承重件抹掉，
> 让后来者以为除一下乘一下就行——那恰恰是被否的那版。

**被否（2026-08-20，制作人当场否决，防翻案）**：
- **S_day / S_new 只用法线朝上项（`nup = normal.y`）、不做任何 march 的写法**。
  症状：逐像素纯调色，画不出巷道与屋檐下的遮蔽结构，**看着就是贴一层滤镜**。
- **照着别的夜景图的统计量（亮度分位/色偏/饱和）去定标调色**。
  症状：本质仍是调色，光没有被重新计算。调色只许作为收尾（管中位亮度与中性色），
  **对比与明暗结构必须由光照扛**。

★ 附带结论：**这条路天然绕开 albedo 反解**——不必知道 albedo 是什么，除法在式子里自己抵消。
⇒ 上一稿提的"离线烘 albedo + S_day"**作废**。

参考实现（经制作人验收，雾津街头 C 版）：`tools/scene_relight/relight.py`
——`sky_field` 天穹可见性、`screen_shadow` 定向光投影、`extract_lamps`/`lamp_irradiance`
伪世界点光、高度雾、调色。**该 numpy 实现是离线参考基准，运行时须以 GLSL 重写并共用
单一真相源（S5）；两边必须做 parity 测试。**

## 2. 立项前就成立的物理约束（不可绕过）

1. **原画里画死的光影是地板**。除旧光只能除掉被 S_day 建模到的那部分，画得很硬的日照墙压不成全黑。
   雾津街头原画本身就画了雾——**做不出"雾津的大晴天"**，要突破只能重画。
2. **深度是单目估计**。雾越浓、阴影越硬，深度误差越显形（屋顶破洞、细栏杆）。
   缓解靠深度笔刷修源，不是加参数。
3. **信息上限**（推导 §16.3）：背景不可见侧的光源、真实三维穿行、绝对 nit 均不可得。
   该文同时指出突破需"法线/材质、额外视图、**人工光源**、完整三维几何"四者之一——
   **本次引入的人工光源正是它钦定的升级路径**，不与理论底座冲突。

#### ★ 3.3.4 影子跟灯：运行时**已经有一套多光源解算**

#### 3.3.7 性能基线

| T9 | 两条已标注实现缺口（`sceneExposureEV` 无人读取；实验室「场景EV」不进烘焙计算路径） | 决策⚠ + character-lighting 已知坑 | **随本次一并了结**：要么实现，要么正式宣告放弃该式 |

## 5. 风险

### 5.1 ★ 会被"不小心复活"的被否方案

| 风险 | 被否原文 | 为何这次特别容易复活 |
|---|---|---|
| **R1（最高）** | **"在屏幕空间直接模糊或积分：无法排除屏幕重合、伪世界深度相离的错误传光"** | **"写一个全屏光照 filter"本质就是屏幕空间**。任何一步在屏幕空间做模糊/衰减/传播（屏幕空间雾、bloom、SSAO、光照溢出）就正面复活这条。**必须逐 pass 论证深度分离** |
| R2 | "把 mask 当亮度阈值用" | 实时化后为省一张图，容易改成"运行时按亮度阈值取灯" |
| R3 | "纯统计亮度或固定 LDR→HDR 肩线" | 实时 tonemap / 自动曝光 / inverse-tonemap 是典型复活路径 |
| R4 | "由通用 agent 逐图目测标发光增益" | **已在复活边缘**：码头白天现有发光 mask 是 agent 猜的灯位 |
| R5 | "运行时携带分割模型" | "全部实时"口号下的顺手违反 |
| R6 | "tint 归一模型" | 若把 `toneEnabled` 并进新光照，注意别退回 tint 归一 |
| R7 | "语义只出候选 + 四重证据裁决 gainEV" | 若"运行时按证据调光强"即复活 07-23 被否的裁决层 |
| **R8（需拍板划界）** | "逐场景堆专用手写规则：维护成本随场景数线性增长" | 实时光照几乎必然引入**逐场景手摆光源列表**。被否原文语境是**发光体判定规则**，不等同于逐场景灯位数据，但边界模糊——**建议作为审批题明确划界**，否则将来会被当成翻案 |

> ✅ **R2/R4 已由 2026-08-20 的架构澄清消解**：灯成为一等数据后，发光体位置与强度**已知**，
> 不再需要从图像猜（既不用亮度阈值，也不用 agent 目测标注）。SAM3 语义门控退出光照路径。

### 5.2 Pixi v8 陷阱：正面撞四条硬契约 + 三条已知坑

| # | 陷阱 | 撞点 |
|---|---|---|
| 1 | 离屏 RT 清屏必须走 `renderer.renderTarget.bind(rt,true,color)`，**`renderer.clear({target})` 不认 target** → 多张 RT 逐帧烘焙会**串台** | **多 pass 光照的头号杀手** |
| 2 | 绑了按场景销毁纹理的对象，卸载时**必须先解绑回占位图再销毁** → 顺序反了**不是泄漏，是把滤镜永久烧毁** | **多纹理绑定的头号杀手**；跨场景长活对象最危险 |
| 3 | 调试链路异常绝不能穿进玩法链路 → 一个坏掉的调试滤镜能让**整场景照明陪葬**，且默认静默 | 光照调试可视化几乎必写 |
| 4 | "alpha 当数据用"的纹理必须 `data.alphaMode:'premultiplied-alpha'` 装载，否则 rgb 在**解码期**就被 ×alpha，GL 层怎么设都救不回 | 法线图/深度图/**可见度图**/发光 mask 全是 alpha 当数据 |
| 坑7 | **`Sprite` 的子节点不渲染**（bounds/visible 全正常、零像素） | 把光照层/雾层挂到角色 Sprite 下是自然写法，**必须挂成兄弟** |
| 坑8 | **`renderer.extract.pixels` 不过 filter、但过 mesh 自定义 shader** | **验证方法论级**：新光照若走 filter 路径，**现有 extract 取证法全部失效**，须先重定验证手段 |
| 坑9 | 隐藏标签页 rAF 暂停，读 uniform 全是初值 | 无头验证时 |

### 5.3 技术债与工程风险

- **世界重建公式已重复 9 处且已出现口径分叉**（§3.3.5）。不先收敛成单一真相源，
  新系统只会把 9 变成 11，且分叉会以"某条路径悄悄退回 billboard"这种静默方式表现。
- **背景加光是全新路径**（§3.3.2），要正面面对"背景层常态 RTT"——代码里已有注释
  明确指出这正是 `BackgroundDebugFilter` 不常驻的原因。
- **每实体一个 filter + 每投影实体一个 blur（auto 下最多 3 槽）**是当前基线开销，
  新增全屏 pass 前应先 profiling（现有怀疑项仍标 SUSPECTED、从未 profiling）。
- **本机无法直接重导出任何场景**（out/ 不存在），迁移必须先重烘，24 场约 1.6 小时。
- **`validate-data` 的 lighting-bake 门刚清零**，格式一改必须同步 `tools/editor/validate.py`，
  否则 28 场景 × 3 文件全量误报，直接破 runtime norms 的审批红线。
- **`renderRaw` 装饰实体**若被新系统吃进光照会集体串色。
- 顺带可清的死码/空转见 §3.3.6（含一个真 bug：`BackgroundDebugFilter` 的
  `uHasGroundTex` 恒 0，碰撞可视化一直是坏的）。

## 6. 审批题（按 constitution §5 格式：题干 / 证据 / 后果）

> §5 规定：报告给 agent 读，**人只收决策题**。以下每题需 yes/no 或三选一。

**Q1（2026-08-20 收窄后重述）— 是否批准把 probe 由"存积分结果"改为"存命中几何"？**
- 证据：`2026-07-21` 决策的"实体受光在伪世界空间积分"经制作人澄清后**保留不变**（T1 已收窄）；
  改的只是辐射场从静态背景换成 relit 背景、积分从离线挪到运行时。当前"换个时刻 = 换输入图 =
  全量重烘"（§3.2.3）与已拍板的 H3「光影连续渐变」不兼容。
- 后果：yes → 原地改写决策卡（幅度比上一稿小得多）+ 升 probe 载荷版本 + 三处登记面同改 +
  28 场景重烘一次换命中图；no → H3 无缝模式永久做不到，日夜只能靠离散换图。

**Q2 ✅ 已答（2026-08-20）** — **题问错了**。角色是片，阴影**只能**是剪影 ⇒
`entity-lighting`「阴影一律 planar 剪影」**不推翻，原样保留**（T7 撤销）。
它管的本来就是**实体**阴影；场景阴影是另一回事（物理 march 深度场）。
两者只在「逐灯可见度 `vis_L`」处汇合（§1.4）。

**Q3 ✅ 已答（2026-08-20）** — **手摆灯**。被否原文说的是**自动判定发光体的启发式规则**，
不是美术摆的灯位数据 ⇒ 风险 R8 撤销，灯位作为场景 JSON 一等数据、编辑器可摆。

**Q4 — 迁移节奏：28 个已烘场景怎么处理？**
- 证据：决策卡有用户级约束"⚠ 已烘场景是用户自己烘的，**不要全量重烘**；迁移由用户按场景推进"；
  但本机 `out/` 已不存在，任何重导出都必须先重烘（§3.2.5），24 场约 1.6 小时（另加首次 SAM3 4–5 分钟/场景）。
- 后果：三选一 →（a）全量重烘一次性换代（b）逐场景迁移 + 新旧载荷并存一段时间（c）先只做 1–2 个试点场景。

**Q6 ✅ 已答（2026-08-20）** — 角色阴影绑定落**实体级**，且**必须可由 Action 控制**。
⇒ 数据形态：`entity.shadow = { source: 'light:<id>' | 'virtual' | 'none', virtual?: {...} }`；
配套需要一个改它的 action（走 `add-game-action` 四件套：运行时注册 + actionParamManifest +
编辑器 ACTION_TYPES/_PARAM_SCHEMAS + validator；灯 id 是实体引用 ⇒ 还要登记 `ENTITY_REF_PARAMS`）。

**Q7 ✅ 已答（2026-08-20）** — 虚拟灯**只管影子，不照亮角色**。
⇒ 模型保持干净：角色的受光**永远**来自 relit 场景 + 真实灯，虚拟灯只进阴影解算，
不进光照合成。与 R9"角色融入场景"无冲突。

**Q8 ✅ 已答（2026-08-20）** — **不反解 albedo**；场景走 §1.6 的 relight
（天穹可见性 + 定向光投影 + 除旧光乘新光），
场景**不接收 AO/GI**，relight 结果即最终表现，同时是角色的辐射源（§1.5）。

**Q5 ✅ 已答（2026-08-20）** — **先走访谈**。unknowns 清单见 §8。

**Q1 ✅ 已答（2026-08-20）** — **批准**。并按工作原则：决策卡改写为与实现对齐，不当路障。

**Q4 ⏳ 待定** — R11「场景全部处理好」倾向全量，但已烘场景的重烘节奏仍需确认（见 §8 U8）。
