## §0 三条铁律(本方案全程不得违反)

| # | 铁律 | 含义 |
|---|---|---|
| **1** | **零动效** | 不得新增任何 `transition` / `animation` / `@keyframes` / spinner / 缓动 / 骨架屏。唯一允许「变化」的是**数据本身的更新**(日志行、阶段勾选、秒数)。 |
| **2** | **状态优先于动效** | 「看得出点没点」靠 `:active` 的**瞬时**翻转实现,0ms 比任何过渡都干脆。补状态,不补动画。 |
| **3** | **不删功能** | 84 个控件一个不少。只做**分层、分组、默认折叠**,不做功能裁剪。专家路径必须保持一键可达。 |

> 铁律 1 的由来:本工具是 WebGL 实时应用,`draw()` 常驻 rAF,README 实测前台仅 **34fps**。任何常驻 CSS 动画都在与渲染循环抢合成帧;而当前唯一的动画(重烘按钮呼吸)使用的是「正在忙」的视觉语言,却被用来表达「参数未应用」,直接导致「整个程序都在卡顿」的误读。

## §1 自我修正(上一轮结论的订正)

上一轮我把「相邻表面对比度 1.02–1.09:1」单列为病灶,**这一条过头了**,先更正:

```
VS Code Dark+  编辑器 #1E1E1E → 侧栏 #252526 = 1.09:1
本工具         面板  #151a1f → 卡片 #171c22 = 1.02:1
```

暗色 UI 里相邻填充比被 WCAG 公式的 +0.05 偏置压缩是**常态**,1.09:1 是业界正常值。所以「填充差太小」不是独立病灶。

**修订后的真实病灶(三者叠加才是「拖沓」):**

| 病灶 | 数据 | 说明 |
|---|---|---|
| A. 控件**既无填充差也无边框** | 按钮面/卡片 1.09:1 **且** 边框/卡片 1.30:1 | 单独看都算正常,**叠在一起** = 按钮既不是一个面也没有一条边 → 不成形、不像可以按 |
| B. **零状态** | `:active`/`:focus`/`:disabled` 各 0 处 | 这才是「看不出点没点」的直接原因 |
| C. **密度无节奏** | 24 处字号全挤 10–13px;`label{margin:4px 0}` × 35 根滑杆 | 同一音量、同一行距,无法扫读 |

结论不变(界面「只画了文字,没画物体」),但**修法**从「拉开填充阶梯」改为 **「强化边框 + 补齐状态 + 建立节奏」**。§2 的 token 已按此重算。

面板仅 316px,**不靠放大字号建立层级,靠字重 + 色 + 间距**:

--fs-title:13px;  /* 区块标题 .st   700 var(--fg) */

### 2.3 状态矩阵(**全部 0ms,禁止 transition**)

```css
select,button{background:var(--s3);border:1px solid var(--bd);color:var(--fg);border-radius:4px}
button:hover,select:hover{background:var(--s3h);border-color:var(--acc)}
button:active{background:var(--s3a);border-color:var(--acc);transform:translateY(1px)}
button:disabled,button[data-busy]{
  background:var(--s1);border-color:var(--bd-soft);color:var(--mut);
  cursor:not-allowed;transform:none}
button:focus-visible,select:focus-visible,input:focus-visible{
  outline:2px solid var(--acc);outline-offset:1px}

/* 主按钮:按下必须可见地变暗 */
button#rebuild{background:var(--acc);color:#14100E;font-weight:700}
button#rebuild:hover{background:#EC8659}
button#rebuild:active{background:var(--acc-a);transform:translateY(1px)}
button#rebuild:disabled{background:var(--s1);color:var(--mut);border-color:var(--bd-soft)}

/* 参数未应用 = 静态标记,不是动画 */
button#rebuild.dirty{box-shadow:inset 0 0 0 2px #FFD54A}

/* 复选框补上主色(现仅 range 有 accent-color) */
input[type=checkbox]{accent-color:var(--acc)}
```

> `transform:translateY(1px)` 无 transition = 瞬时位移,属状态不属动画,符合铁律 1。若仍嫌多余可去掉,保留变暗即可。

### 6.3 施工中发现并修复的**额外 bug**(方案里没写、实际动手才暴露)

1. **`setView()` 无作用域选择器**:`.views` 类被主视图切换器与 `#cam_modes`/`#pano_modes` 共用,`document.querySelectorAll('.views button')` 会把相机/全景按钮的 `.on` 一起清掉;而 `setCamMode` 有 `if(m===c.mode) return` 守卫 → **高亮一旦被清就再也回不来,UI 对当前模式说谎**。已作用域到 `#view_tabs`,并真机验证三次切视图后 `fly` / 全景 `关` 高亮不丢。
2. **`.row2` 用了 5 次却从未定义 CSS**:三组本该并排的按钮全部堆成整行。已补真两列 grid。
3. **悬停实例读数被每帧 HUD 覆盖**:`mousemove` 写 `$('hud').textContent`,而 `draw()` 每帧无条件重写 HUD → 读数下一帧就没,等于功能不存在。已改为并进 HUD 合成。
4. **`pipeline.py` 阶段输出块缓冲**:多数阶段 `print` 没有 `flush=True`,子进程 stdout 是管道时默认块缓冲 → 所有阶段标签憋到进程退出才一次吐出,阶段清单全程停在"未开始"。修法是 `subprocess` 用 `python -u`(**不可省**)。
5. **`[hdr]` / `[char]` / `[depth]` 缓存分支不打标签**:会让阶段清单把"跑过了/用了缓存"显示成"跳过"。已补三行 `flush=True` 进度输出(不动算法与产物格式)。

### 6.6 `audit-walkable` 的 8 条「NPC 卡墙」是假阳性 —— 真 bug 在别处

首轮把这 8 条归为「既存数据问题、待内容侧修」。**复核后这个结论是错的**:它们根本不是问题,
而体检器本身有缺陷。读运行时源码取证(全部 file:line 可查):

- `src/entities/Npc.ts` **全文 0 处碰撞引用**;全项目 `isCollision` 只有两个调用点 ——
  `src/core/Game.ts:2254`(玩家碰撞回调)与 `src/entities/Player.ts:353`。
- `Npc` 类**没有 `update()`**,每帧唯一入口是 `Npc.ts:601 cutsceneUpdate`;静止 NPC 在里面
  只落到 `Npc.ts:643 sprite.update(dt)` 推进动画 —— **不被推开、不卡住、不报错**。
- patrol 推进是 `Npc.ts:637-638` 的裸直线插值(`this.x += nx*step`),前后无任何碰撞守卫
  → 起点在阻挡格里**照样走得出去**,不会原地卡死。
- NPC 的 x/y **不写入**玩家碰撞:`Game.ts:2260-2264` 只在该 NPC 配了 `collisionPolygon` 时
  才参与(`utils/hotspotCollision.ts:27-28` 无此字段即 `return null`)。全库仅 `码头白天` 3 个。
- `fx_*`(如 `fx_steam_2`)是住在 `npcs` 数组里的**装饰特效**:无 patrol、无 collisionPolygon、
  `interactionRange:0`、`castShadow:false`。热气灯光本来就该长在灶台柱子这类阻挡几何上 ——
  **摆到可走地面反而是错的**。

> 这与该文件早已清理掉的 `moveEntityTo` 那条是**同一个陷阱**(见 `audit_walkable.py` 尾部注释
> 「完全可信但完全错误」):判据本身没错,但**被判对象根本不走那条代码路径**。
> 按原结论去批量挪 NPC,会把摆好的特效和靠墙站位全部打散 —— 这也正是该文件开头
> 「只报不改…批量吸附会把摆好的人打散」那条注释在防的事。

**已改**(`audit_walkable.py`):默认只查**真有运行时后果**的一类 —— 配了 `collisionPolygon`
的 NPC(会往玩家碰撞里写多边形,可能封死窄通道);普通 NPC 落点降级为 `--npc` 选装自查项。
并留注:静止 NPC 真正值得担心的是「玩家能否走进 `interactionRange` 触发对话」,那是**可达性**
问题,得拿玩家可达区做 flood fill 才测得准,不能用「落点是否阻挡」顶替。

**噪声去掉后浮出一个真 bug**:`mountain_pass` 有两个出生点**整个落在世界之外**
(世界 1500×941,而 `from_street` y=1496.6、`spawn_0` (1597.5,1538))。而且是**可达路径**——
`河边.json` 的 warp 指向 `mountain_pass/spawn_0`,`test_room_a` 指向 `from_street`;
界外运行时按「不阻挡」处理,所以玩家会掉出地图并在虚空里乱走,**既不报错也没人拦**。
老 `--fix-spawns` 只查 `is True`(阻挡),把「越界」这一类整个漏掉。已补:先夹回世界内
(保留原本的边缘意图),再就近吸附可走点。实际改动 = **4 个数字**:

```
spawnPoints[from_street] (66.1,1496.6) → (66.1,911.0)
spawnPoints[spawn_0]     (1597.5,1538.0) → (1470.0,911.0)
```

写盘经 load→dump **字节级幂等**校验(证明未重排键、未重格式化),编辑器往返契约
(`ensure_ascii=False` / 2 空格 / 末尾换行)保持。⚠ 落点位置是设计可见的,建议制作人
在主编辑器里按"从街道/从河边进来该站哪"再微调一次。
