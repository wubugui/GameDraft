## 一、结论摘要

1. **「配角」这条能力今天就有**：`SceneData.npcs` + `characterId` 引用注册表，编辑器可配。
   不用做任何事。真正缺的是后三条。
2. **同屏基本已通**：深度排序、逐像素光照、投影阴影、透视缩放全是逐实体的。
   唯一缺口是 **NPC 没有行走面碰撞**（只有玩家有），配角一旦自己走就穿墙。
3. **跟随完全没有**，而且有个数据模型级的坑：实体只有两种寿命（场景级 / 过场级），
   **"跟着玩家切场景"在数据模型里没有落点**。必须新增第三种：**随行级**。
4. **受控是单例硬编码**：`Game.ts` 里 `this.player` 出现 82 次，`Player.entityId` 写死 `'player'`。
5. **核心主张**：把 `'player'` 从"某个实体的名字"改成**"当前受控者的别名"**。
   这一条让**现有全部对话/动作/过场 JSON 零改动**自动跟随切人 —— 是整个方案里性价比最高的决定。
6. **两种跟随共用一套行为**，区别只在"谁负责在新场景里把它变出来"：
   剧情段跟随 = 场景里正常摆的 NPC + `startFollow`；长期同伴 = 随行队伍 + 自动实例化。
7. 建议**分五期**，P0/P1 两期不依赖任何玩法决策、无论最后走到哪一步都要做。

## 二、现状调查（事实与出处）

### 2.1 同屏：哪些已经是逐实体的

| 子系统 | 状况 | 出处 |
|---|---|---|
| 深度排序 | 按脚点 y + 排序带，与实体类型无关 | `Renderer.ts:188-213` |
| 逐像素光照 | `litShaders` 是集合，逐 entity 生效 | `CharacterLightingSystem.ts:939` |
| 投影阴影 | 注释即「为玩家与各 NPC 重建」 | `Game.ts:2986` |
| 透视缩放 | `Npc.setPerspectiveScale` 已有 | `Npc.ts:270` |
| 相机跟随 | `cameraFollowActor` 按 id 解析，不绑主角 | `Game.ts:1398, 5271` |
| **行走面碰撞** | ⚠ **只有玩家** | `Game.ts:2923` `this.player.setDepthCollision(...)`；`Npc.ts` 全文无 collision |

### 2.2 跟随：现有移动能力与缺口

- `Npc` 只有 `patrol`（固定路点循环）与 `moveTo`（一次性到点，`Npc.ts:569`）。
- 没有 follow 行为、没有角色间避让、没有寻路。
- **跨场景是硬缺口**：NPC 是场景级实体（`SceneData.npcs`），持久化的 `sceneMemory`
  **按 sceneId 分桶**（`SceneManager.ts:77`）。今天实体只有两种寿命：
  **场景级**（NpcDef）与**过场级**（`_cut_` 临时演员，`Game.ts:1097`）。

### 2.3 受控：单例的分布

- `Game.ts:305` `private player: Player`；`Game.ts:521` 构造期唯一 new。
- `Player.ts:96` `get entityId() { return 'player'; }` —— id 硬编码。
- `Game.ts:1095-1102` 唯一 `resolveActorFn`：临时演员 → 场景 NPC → `id === 'player'`。
- `this.player` 在 `Game.ts` 出现 **82 次**。绝大多数是 `.x/.y` 与 sprite 操作（机械替换），
  真正要成对处理的是**六个注入点**：

  | 注入点 | 出处 |
  |---|---|
  | `setDepthCollision` | `Game.ts:2923` |
  | `setPerspectiveScale` | `Game.ts:3696, 3718` |
  | `setMovementModifier`（位面漂移） | `Game.ts:1305` |
  | 像素密度匹配 | `Game.ts:4711-4712` |
  | 烘焙着色 / 深度滤镜 | `Game.ts:3813-3832` |
  | 光环境曲线采样点 | `Game.ts:2966, 3235` |

  **漏摘任何一个 = 切人之后静默错**（角色不受碰撞 / 光照停在旧位置 / 滤镜挂在错的精灵上）。
  这是本方案最容易埋雷的地方，见 §四.3 的对策。

### 2.4 身份体系：主角与 NPC 是两套不通的东西

| | NPC | 主角 |
|---|---|---|
| 身份定义 | `character_registry.json` 一条 | 散在三处 |
| 外观 | `animFile` | `game_config.playerAvatar.animManifest` |
| 显示名 | `name` | `strings.json` `dialogue.defaultProtagonistName` + flag `player_display_name` 覆盖 |
| 立绘 | `portraitSlug` | `playerAvatar.portraitSlug`（经 `setPlayerPortraitSlugProvider` 单个注入） |
| characterId | 有 | **无** |

而且 `playerAvatar` 里装着 NPC 完全没有的东西：**idle/walk/run 三态映射、六个身体动词
（蹲/蹲行/注视/踢/跳/躺）、待机节目单**（`types.ts:1946-2000`）。
**一个配角要能被接管，就必须有这一整套 —— 今天没地方放第二份**
（`player_avatar_editor.py` 646 行编辑的就是那唯一一个 dict）。

### 2.5 存档

走 `registeredSystems` 的 `serialize()/deserialize()` 收集分发（`Game.ts:4319-4345`），
新增一个系统条目即可挂进去，**不需要动 SaveManager 结构**（`SAVE_VERSION` 仍为 1）。

## 三、数据模型

### 3.1 三种角色寿命（新增第三种）

| 寿命 | 载体 | 谁实例化 | 现状 |
|---|---|---|---|
| 场景级 | `SceneData.npcs[]` | SceneManager 装载场景时 | 已有 |
| 过场级 | `_cut_*` 临时演员 | CutsceneManager | 已有 |
| **随行级** | **随行队伍（运行时列表）** | **Game 在每次场景装载后动态建** | **新增** |

**随行成员不写进任何 `SceneData`** —— 它跟着人走，不属于任何场景。
落点 = 玩家出生点附近的偏移位（进场时吸附，见 §四.4）。

### 3.2 角色身份收口：`avatar` 段进 CharacterDef

```jsonc
// character_registry.json
{
  "id": "guan_ergou",
  "name": "关二狗",
  "animFile": "/resources/runtime/animation/player_anim/anim.json",
  "portraitSlug": "player",
  "avatar": {                          // ⭐ 新增：有这段 = 这个角色可被接管
    "stateMap": { "idle": "idle", "walk": "walk", "run": "run",
                  "crouch": "crouch", "kick": "kick", "jump": "jump", "lie": "lie" },
    "idle": { /* 待机节目单，结构同现 PlayerIdleConfig */ }
  }
}
```

- **`avatar` 段的结构就是今天的 `PlayerAvatarConfig` 去掉 `animManifest`/`portraitSlug`**
  （那两项本来就是 CharacterDef 已有的 `animFile`/`portraitSlug`）—— 是收编，不是新造。
- **"某逻辑名解析不到片段 = 该动词在本角色下自动禁用"这条现有语义原样保留**
  （`types.ts:1951` 注释）。配角没有 `kick` 片段就是踢不了，不需要额外开关。
- 主角关二狗**建成一条普通 CharacterDef**，与配角同构。

### 3.3 game_config 的迁移

```jsonc
{
  "initialControlledCharacter": "guan_ergou",   // ⭐ 新增
  "initialParty": ["guan_ergou"],               // ⭐ 新增（有序，[0] 为初始受控）
  "playerAvatar": { … }                          // 保留：旧档/未迁移工程的兼容读法
}
```

**兼容规则**：`initialControlledCharacter` 缺省时，用 `playerAvatar` 就地合成一条匿名角色
（id 固定 `__legacy_player__`），行为与今天逐字节一致。**迁移不是硬门槛。**

**两条必须守住的解析口径**（P0 审查抓到的语义反转，落点 `characterRegistry.resolveAvatar`）：

- **装扮换了包又没显式给 `portraitSlug` ⇒ 立绘留空，由消费侧按新包目录名推导。**
  现行 `setPlayerAvatar` 就是这个语义（扛尸换包 ⇒ 头像换成扛尸立绘）。
  若回落到角色本体的 slug，扛着尸体说话会用常态立绘 —— 正好反掉。
  只有**没换包**的纯状态换装才继承本体立绘。
- **角色漏填 `animFile` 时不兜底到玩家默认包。** 兜底会让漏填的配角顶着关二狗的动画
  和立绘上场（同屏两个关二狗）且零告警。运行时留 `undefined`，构建期由 validator 拦。

### 3.4 换装（`setPlayerAvatar`）的归位

今天换装是散装参数，内容里 3 处调用**复制了三份一模一样的 `stateMap`**
（`pressure_holds.json:49/116/375`）。收编为**命名装扮**挂在角色下：

```jsonc
"avatar": {
  "stateMap": { … },                      // 常态
  "outfits": {                            // ⭐ 命名装扮
    "carry_corpse": {
      "animFile": "/resources/runtime/animation/player_carry_corpse_anim/anim.json",
      "stateMap": { "idle": "carry_idle", "walk": "carry_walk", "run": "carry_heavy_walk" }
    }
  }
}
```

`setPlayerAvatar` 新增 `outfit` 参数（旧的 `bundleId`/`animManifest`/`stateMap` **全部保留**，
按现有语义继续工作）。这一项**可以独立先做**，不依赖多角色的任何决策。

### 3.5 存档新增段

```jsonc
"partySystem": {
  "controlled": "guan_ergou",
  "party": ["guan_ergou", "axiu"],
  "followers": { "axiu": { "mode": "party" } },
  "positions": { "axiu": { "x": 412, "y": 388 } }   // 仅当前场景内的落位
}
```

旧档无此段 → 回落 `initialControlledCharacter` / `initialParty`（= 多角色出现前的语义）。

## 四、运行时设计

### 4.1 核心决定：`'player'` 变成"当前受控者"的别名

`resolveActorFn`（`Game.ts:1095`）第三段从
`if (id === 'player') return this.player`
改为
`if (id === 'player') return this.controlled.actor`。

**收益（这是本方案的支点）**：
- 全部现有 JSON 里写 `player` 的动作目标、过场演员、镜头跟随，**语义自动变成"当前受控者"，零内容改动**。
- 对话说话人 `kind:'player'`（`types.ts:528`）同理 —— 名字（`GraphDialogueManager.ts:1149`）、
  立绘（`resolvePortrait`）、左右分边（`dialogueSpeakerSide.ts:26` 判 `kind==='player'` → 右侧）
  **全部自动跟随切人**。
- 要点名某个具体角色说话，已有 `kind:'sceneNpc'` + npcId，够用，不新增枚举。

同时每个角色实例保留**自己的真 id**（如 `npc_axiu`），可被单独点名。
**`'player'` 与真 id 同时可寻址，前者是别名。**

### 4.2 受控 = 一组注入的挂载，不是一个类

**不合并 `Player` 与 `Npc` 两个类**（486 + 796 行，一次合并回归面太大）。做法：

1. 抽 `IControllableActor` 接口 = `Player` 现有 API 的子集（`Player.ts:98-294` 那批）。
2. **`Npc` 补齐它缺的**：`setDepthCollision` / `setMovementModifier` / `setPostureMovement` /
   `setAnimationOwnedByAction` / `setAnimationOwnedByIdle` / `setInputLocked` /
   `syncMovementFromScene` / walkSpeed·runSpeed / **输入驱动的 update 分支**。
   —— 其中 `moveTo`/`jumpTo`/`cancelMotion` **两个类今天已是近乎逐行重复的两份**，
   本期正好抽成共享 movement helper（**这是顺手的债务清理，不是额外成本**）。
3. `Player` 类保留但**去掉硬编码 `entityId`**；长期看它会退化成"关二狗这个角色的实例"，
   最终可删 —— 但**不在本方案范围内**。

### 4.3 切换 = 一个 attach/detach 的单一函数（防漏挂）

§2.3 那六个注入点是最容易埋雷的地方。对策：

```
ControlledSlot.attach(actor)   // 六项全挂 + 输入接管 + 相机跟随 + 系统换绑
ControlledSlot.detach()        // 六项全摘，且必须能还原成"普通 NPC"
```

- **禁止在别处零散调用这六个 setter**（同 `PlaneReconciler` 的"只写自己的通道"纪律）。
- 配一个**成对性测试**：attach→detach 后目标实体的六项状态必须回到基线。
  这类"漏一个就静默错"的东西，知识库里已有前车之鉴（显隐四通道、flush 钩子鸭子协议）。
- 需要换绑的系统：`PlayerActionSystem`（`this.player` 只读字段，`PlayerActionSystem.ts:107`）、
  `PlayerIdleBehaviorSystem`、`InteractionSystem` / `ZoneSystem`（**这两个已经是注入 getter，
  最轻**，`Game.ts:2696`）、`HealthSystem`、`SmellSystem`（后两个的归属是玩法问题，见 §七）。

### 4.4 跟随：两种模式共用一套行为

新增 `FollowSystem`（`IGameSystem`，进 `registeredSystems`）：

- **目标点用领队的轨迹面包屑**（breadcrumb 队列：领队每移动 X 世界单位入一个点，
  跟随者追队列里落后 N 单位的那个点），**不要"直接朝领队走"** —— 面包屑能自动过窄道、
  自动排队，且不需要寻路。
- 到达阈值内停下播 idle；领队瞬移/切场景 → 直接吸附，不追。
- 角色间软避让：最小间距推开即可，不做完整碰撞。
- **依赖 §四.5 的 NPC 碰撞**，否则跟随者会切角穿墙。

两种模式的差别**只在"谁负责在新场景里把它变出来"**：

| 模式 | 触发 | 谁实例化 | 切场景 |
|---|---|---|---|
| **剧情段跟随** | `startFollow(npcId)` 对场景里已摆的 NPC | 场景 JSON（现状） | 跟随随场景结束而止 |
| **长期同伴** | `partyAdd(characterId)` | **Game 在场景装载后动态建** | 自动带过去 |

行为完全共用；`stopFollow` 两者通用。

**领队 = 当前受控者，不是某个固定角色**（拍板 #2）。切人时：

- 领队指针跟着受控槽走；**新受控者立刻从跟随列表里摘掉**（自己不能跟自己）。
- **面包屑队列必须清空重建** —— 不清的话新领队的跟随者会去追旧领队留下的轨迹，
  表现为"同伴集体朝一个没人的方向走"。这是本条最容易漏的实现细节。
- 原受控者转为跟随者，用它当前位置作为面包屑起点，不吸附（原地自然接上）。

### 4.5 NPC 补行走面碰撞

把 `Game.ts:2923` 那段深度场碰撞判定抽成 factory，对**移动中的** NPC 也注入。

**性能注意**：场景内 NPC 有 92 个量级，不能每个每帧都查深度场。
只有"本帧有位移意图"的实体才查（跟随者、巡逻中、`moveTo` 段内），静止 NPC 零开销。

**默认关，不是默认开**（P0 落地口径）：`Npc.setDepthCollision(null)` = 现状行为。
既有 92 个 NPC 的巡逻路线正是按"不挡"编排的，默认开会让贴墙路线当场卡住。
只有需要沿地面自行走路的实体（同伴）才注入。

#### ⭐ 编排位移不吃碰撞（2026-08-06 拍板，与 Player 对齐）

这是本域的**唯一口径**，两侧完全对称：

| | 编排位移（**不**吃碰撞，穿墙直达） | 自行走位（吃碰撞） |
|---|---|---|
| Player | `moveTo` / `jumpTo` | `update()` 输入驱动 |
| Npc | `moveTo` / `jumpTo` | **`steerBy(dx, dy)`** |

理由：不对齐的话，`'player'` 变成受控者别名之后，同一条 `moveEntityTo` 会因为
"当前受控的是谁"而表现不同 —— 编排好的演出走位会随玩家切人而变，不可接受。

`Npc.steerBy` 是无状态原语（给多少走多少、逐轴钳制、返回是否真挪动），
转向/跟随距离/动画/朝向全归调用方（P2 的 FollowSystem）。它不碰 `moveTarget`，
与在途编排位移互不干扰。

**连带结论**：编排位移永远走得到，所以 `moveTo` 的 Promise **不存在"被墙挡住而悬挂"**
这类失败，不需要放弃兜底。（P0 曾按"moveTo 吃碰撞"实现并配了推进量兜底，
对齐拍板后该兜底成为死代码，已删。教训保留在 `collisionStep.ts` 的注释里：
`moved` 为 true 不代表离目标更近，贴墙渐近滑行时两者会背离。）

**P2 待补（跟随落地时一起做）**：`stepWithCollision` 目前只有碰撞判据，缺 `isOutOfBounds`
（Player 每轴还判世界边界）。跟随者一旦注入碰撞就能走出地图边界。收编 `Player.update`
到同一个 helper 时一并解决。届时 Player 与 Npc 的自行走位真正合流成一份实现。

### 4.6 新增 Action（每个都走四件套）

| Action | 参数 | 说明 |
|---|---|---|
| `switchControlledCharacter` | `characterId` | 切人；目标必须在队伍内且当前场景有实例 |
| `partyAdd` / `partyRemove` | `characterId` | 长期同伴进出队 |
| `startFollow` / `stopFollow` | `target`（实体 id） | 剧情段跟随 |

四件套 = 运行时 `register` + `actionParamManifest.ts`（TS 权威）+ 编辑器 `ACTION_TYPES`/`_PARAM_SCHEMAS`
+ validator 认可（`agent_docs/runtime/mechanisms/action-registration-quadruple.md`）。
**`startFollow`/`stopFollow` 含实体引用参数，必须另登记 `ENTITY_REF_PARAMS`**（第五件，
否则 `entity_refactor` 改名/迁移时引用会静默断，`content/mechanisms/entity-refactor-engine.md`）。

### 4.7 过场边界契约（拍板 #4）

**规则**：进入任何 cutscene → 立即切回关二狗 + 其它角色立即隐藏。

这一条把"同伴在过场里站哪"整类问题消掉了 —— **所有现有过场都是按"场上只有关二狗"编排的，
这条规则让它们全部保持原样正确**，是本方案里第二划算的决定。但它引入三个必须写死的边界：

**① 钩子用现成的，不新造**

`CutsceneManager` 已发 `cutscene:start` / `cutscene:end`（`CutsceneManager.ts:528/611/658`），
且**保证 end 恰好发一次**（异常路径有兜底分支，注释见 `CutsceneManager.ts:1533`）。
直接挂这两个事件，不要在 `startCutscene` 调用点自己包 —— 调用点有三处以上（
`Game.ts:4237/4306`、图对话内），包漏一处就是同伴留在过场里。

**② 隐藏必须走独立通道，禁止 `setVisible`**

`agent_docs/runtime/mechanisms/entity-visibility-channels.md` 是硬契约：
显隐由四个独立通道在实体内单点合成，**任何一方只写自己那条，禁止直接 setEnabled/setVisible**。
过场隐藏同伴要**新增第五条通道** `partyHiddenForCutscene`，不要挪用会话覆盖通道
（内容侧的 `setEntityEnabled` 也写那条，两边会互相冲掉）。

**③ 出过场怎么恢复 —— 本文的默认，需你确认**

拍板只说了"进"，没说"出"。本方案取**对称还原**：

| 项 | 出过场时 |
|---|---|
| 受控者 | 恢复进过场前的那个（**除非**过场内显式调了 `switchControlledCharacter`，则以显式调用为准） |
| 同伴显隐 | 第五通道清空，恢复原显隐 |
| 同伴位置 | **吸附到受控者身边**（过场可能移动了主角，甚至换了场景） |

理由：这条规则的动机是"过场按关二狗编排"，那么切回关二狗就是**过场期间的临时接管**，
过完还回去最不意外。若你要的是"过完就保持关二狗"，改一行，但请明说。

**④ 两个硬约束**

- **关二狗恒在队伍，不可 `partyRemove`** —— 否则"切回关二狗"无处可切。
  违反时 action 拒绝执行并 warn，不静默。
- **图对话不是 cutscene**。对话期间同伴照常在场上、照常显示。
  只有 `GameState.Cutscene` 触发本规则。这条要写进机制卡，否则内容侧一定会误解。

## 七、拍板记录与后果（2026-08-06 全部已定）

### 7.1 血量 / 气味 / 背包 = 整个队伍一套

**后果：`HealthSystem`、`SmellSystem`、`InventoryManager` 三个系统零改动。**
它们本来就是队伍级单例，只是过去"队伍"恰好只有一个人。切人不碰这三者。

顺带确认一条语义：**气味是"队伍闻到的"，不是"某个角色闻到的"** —— 象理术的读数来源
不因切人而变。`Q` 键闻的仍是当前受控者位置的气味场（位置变了读数自然变，这是对的）。

### 7.2 切人后其它成员跟随新受控者

见 §4.4 的三条实现要点，其中**面包屑队列必须清空重建**是最容易漏的。

### 7.3 配角可用身体动词（身体动词是机制）

`PlayerActionSystem` 从"持有 `player` 只读字段"（`PlayerActionSystem.ts:107`）改为
跟受控槽换绑。**"某逻辑名解析不到片段 = 该动词在本角色下自动禁用"这条现有语义原样生效**
（`types.ts:1951`）—— 配角的动画包里没有 `kick` 就是踢不了，不需要任何额外开关，
也不需要为配角补齐六个动词的片段才能上线。

### 7.4 进过场切回关二狗 + 其它角色隐藏

见 §4.7 的完整边界契约。**其中"出过场怎么恢复"是我替你定的默认（对称还原），
若要改成"过完保持关二狗"请明说。** 另两条硬约束：关二狗不可移出队伍；图对话不适用本规则。

### 7.5 玩法需求清单已对齐

已在 `docs/玩法功能需求清单.md` 新增 **B4. 多角色与同伴系统**（2026-08-06 拍板）。

## 八、已知风险

- **六个注入点漏摘**（§2.3）：最可能的静默 bug 源。对策 = 单一 attach/detach 函数 + 成对性测试。
- **`Player`/`Npc` 移动代码两份**：本方案抽共享 helper 而非合并类，降低回归面；
  但两份代码在过渡期仍需同步改动，属已知成本。
- **NPC 碰撞的性能**：92 个 NPC 全量每帧查深度场会掉帧。必须只查"有位移意图"的（§4.5）。
- **跨场景同伴的落位**：进场吸附点若压在不可行走区或热点上，会出现同伴卡住/挡交互。
  需要一个"从出生点向外找最近可行走点"的兜底。
- **存档兼容**：旧档无 `partySystem` 段 → 回落初始配置。**不要提 `SAVE_VERSION`**（结构是 additive）。
- **`entity_refactor` 未覆盖**：新 action 的实体引用参数不登记 `ENTITY_REF_PARAMS`，
  改名时引用静默断。这是已入库红线，不是新风险。
- **与「角色统一为 NPC」的耦合**：那条线正在把 39 个占位角色出包。
  本方案的 `avatar` 段**只给可控角色填**，占位角色不填 —— 两条线互不阻塞，但角色页会同时被两边改，
  建议错开落地窗口。

拍板后新增的三条（全部来自 §4.7）：

- **过场钩子包漏**：`startCutscene` 调用点有三处以上，必须挂 `cutscene:start`/`cutscene:end`
  事件而不是在调用点自己包。包漏一处 = 同伴留在过场里。
- **隐藏通道打架**：过场隐藏同伴若挪用会话覆盖通道，会与内容侧 `setEntityEnabled` 互相冲掉。
  必须新增第五条独立通道（显隐四通道是硬契约，不是建议）。
- **"图对话不是 cutscene"会被内容侧误解**：这条必须写进机制卡，否则策划会以为对话里同伴也消失。
