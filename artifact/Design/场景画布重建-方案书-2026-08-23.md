# GameDraft 场景画布重建方案书

**版本** 2026-08-23 · **状态** 待拍板 · **适用分支** `lighting-rebuild` / worktree `canvas-rebuild`
**本文所有行号均已在本仓实测核对**（`tools/editor/editors/scene_editor.py` 实测 16037 行）。

## 摘要（给不写代码的人）

老画布不是"bug 多"，是**同一个结构缺陷长了三十张脸**。缺陷只有一条：**这个画布没有唯一的写入口**——每一次鼠标拖动都自己决定"数据往哪份写、要不要标记未保存、要不要留一份可撤销的底稿"。于是"哪份数据是真的"变成了一条要在几十处代码里各自记住的口头约定，谁忘一处，就多一种"看着对、存下来错"的坏数据。

方案是把这条约定从"人要记住"变成"程序结构上做不到别的"：采用 **Document–View–Command**（Tiled 编辑器与 Qt Undo Framework 的成熟做法）。在这套架构下，画布只能看不能写，所有修改必须做成一个"命令对象"交给唯一的文档去执行——于是"写错副本""撤销撤一半""点一下就变脏"这几类问题**不是被修好了，而是在新结构里没有地方可以发生**。

同时明确一条边界：**"编辑器里看到的和游戏里跑出来的不一样"这个问题，换架构治不了**，它是另一个病（编辑器有第二份渲染实现），必须单独立项、用已经在产的运行时内编辑通道解决。把两件事捆在一起做，是这次重建最可能失败的方式。

工作量：最小可用版本约 **5000 行新代码 / 2–2.5 人月**，替换掉老文件里 6490 行画布代码；**属性面板 6657 行、外壳与共享数学约 3000 行确认零改动复用**——这是本方案成立的最大既得利益。

## 一、诊断：那几十个"痴呆问题"的共同根因

### 1.1 一句话根因

> **老画布把"数据的真相在哪"交给了每一处鼠标手势自己判断。**

展开成三个可验证的事实：

1. **同一份数据同时有两到三个可写副本**：模型里的 `model.scenes[sid]`、属性面板持有的深拷贝 `_staging_hotspot/_staging_npc/_staging_zone/_staging_scene`、以及控件里正在被用户敲的值。谁是真的取决于"当前有没有实体被打开"（`scene_editor.py:14736` `_commit_pending_scene_edits` 的提交顺序注释直接写明了这个双层结构；`scene_undo.py:1-18` 模块头也把它称作"两层真相"）。
2. **写入者是分散的**：`SceneCanvas` 有 **29 条信号 + 81 个公共方法**（实测），每一条几何提交、每一次拖动、每一次微移都是一条独立的写入路径，各自决定写哪一份。
3. **"标记为已修改"是手写的两级动作**：既要 `model.mark_dirty("scene", sid)`，又要 `_props._set_pending_dirty(True)`，两者缺一即半份写入（`scene_editor.py:14723-14734`）。

### 1.2 表象 ≠ 根因

盘点里那份"血泪注释"清单，每一条读起来都像一个独立的历史事故。它们不是。下表左列是**用户看到的现象**，右列是**结构上缺的那样东西**——注意右列只有 7 项，而左列可以无限长下去。

| # | 用户看到的现象（表象） | 老画布的补丁在哪 | 结构上缺的是什么（根因） |
|---|---|---|---|
| 1 | 拖完实体，画布位置对了，右边属性面板的数字**弹回旧值** | `SceneEditor._on_item_selected` 必须"已在编辑同一实体就短路"（盘点 SEL-01） | **缺唯一写入口**：面板与画布是两个都能写的副本，谁后写谁赢 |
| 2 | 整组拖动后，**组里少一个人跟上**，画布还照新位置画，肉眼看不出坏数据 | `_group_member_write_dict`（`:13028`）逐成员判断"写 staging 还是写模型" | 同上。写入目标由手势代码现场判断，判错即静默坏数据 |
| 3 | 只是**点一下看属性**，坐标就被写了、场景被标脏、原本是整数的坐标漂成小数 | 三道零位移闸：press 快照比对、`_xy_unchanged`、`_keep_num`（盘点 DRAG-02） | **缺"变更 = 对象"**：没有 Command，就没有一个统一的地方能问"这次到底变了吗" |
| 4 | 整组拖到一半按 **Esc，退不回原处**，坐标被悄悄截断成一位小数 | `_SceneGroupBox.cancel_gesture`（`:2380`）改用按下时的快照精确回灌 | 同上。没有"命令构造时抓 before"的统一时机，只能靠反算增量 |
| 5 | 按住方向键微移一秒，**要按 30 次 Ctrl+Z** 才退得回去 | 400ms idle timer 手工收口（`_finish_nudge_session` `:13693`） | 同上。没有命令合并（`id()` + `mergeWith()`），只能每处自己糊一个定时器 |
| 6 | 删除实体/切场景时**编辑器直接闪退**（段错误） | 满仓的 `QTimer.singleShot(0, self, ...)`、"删 overlay 前先 `setSelected(False)`" | **缺"删除前置事件"**：没有 `AboutToBeRemoved` 契约，视图只能靠人肉记住清引用的时机 |
| 7 | 旋转手柄**点不动**，一按就变成拖整个 Zone | 叠放循环点选的抬 z 必须是"栈内相对 +1"而非绝对置顶（`:3802-3849`，护栏 `test_scene_canvas_z_layers.py`） | **用显示状态兼职承载命中语义**：z 本是"画在哪层"，被拿来当"该派给谁" |
| 8 | 提示写着"双击边线插点"，**实际怎么点都没反应**（巡逻折线、光曲线两处） | 无。至今未修，因为没有任何交互级测试覆盖 | **缺"绘制形状 / 命中形状"分离**：`shape()` 一个函数既管画又管点，两个需求互斥 |
| 9 | 大场景缩放后，多边形顶点**只有 3 像素**，根本按不中 | 分组框那一族已改成按屏幕像素定尺，顶点手柄没跟上（`HANDLE_WORLD_R=14` 仍是世界单位） | **缺命中尺寸的统一换算层**：世界单位与屏幕像素两套并存，改一处补一处 |
| 10 | 在画布上摆灯**点错了没法 Ctrl+Z** | 无。`_on_light_place_requested` 漏了 `self._undo.capture(...)`，同族的光曲线、透视轴都有 | 同 #3。撤销是"每处记得写"而非"写入本身就会入栈" |
| 11 | 新增出生点后**又被静默抹掉**（同族事故记录了两次：P1-01 / P1-25） | 每条增删路径前手动补 `_commit_pending_scene_edits()`（`:15610`、`:15845` 各一段注释） | **缺变更通知总线**：29 条画布信号 + 21 条面板信号 = 50 条点对点接线，新增一条路径要记得接上前面所有约定 |

**结论**：这 11 行右列压缩成 7 条结构缺陷，7 条压缩成 1 条根因。所以"修 bug"是修不完的——每修一个，就在某处再加一条要记住的约定，而约定的总数只会单调上升。老画布 16037 行里那些长篇血泪注释，正是这条曲线的物证。

## 二、架构选型：拍板

### 2.1 推荐架构（一个，不是几个）

> **Document–View–Command。出处：Tiled 编辑器（`mapeditor/tiled`）的 `Document` / `ChangeEvent` / `QUndoCommand` 三层，以及它所基于的 Qt Undo Framework（<https://doc.qt.io/qt-6/qundo.html>）与 Qt Model/View（<https://doc.qt.io/qt-6/model-view-programming.html>）。**

技术栈**保持 Qt / QGraphicsView 不变**，以新 page 类 `SceneEditorV2` 落地，老画布原样保留。

三层的分工（Tiled 原样，不改名、不发明）：

```
Tool（手势）──构造──► Command（唯一能写的东西）──►Document（唯一的数据 + 撤销栈 + 选择态）
                                                        │
                                     Command 自己 emit ──┘
                                                        ▼
                                             changed(ChangeEvent)
                            ┌──────────────┬────────────┴────────┬──────────────┐
                            ▼              ▼                     ▼              ▼
                      SceneMapItem   SelectionOverlay        当前 Tool    ScenePropertyPanel
                      （建/删子图元）  （选中框/标签）        （更新可用性）   （已有 6657 行，复用）
```

**没有一条反向箭头。** View 从不写数据；Tool 从不直接写数据；数据不知道 View 存在。

### 2.2 为什么这几类 bug 在这套结构下"物理上不可能"

不是"更容易修"，是"没有地方可以发生"。逐条：

| 老 bug 类 | 为什么新结构里做不出来 | Tiled 出处 |
|---|---|---|
| **写错副本 / 半份写入**（表象 #1 #2 #11） | View 与 Tool 对数据**只读**，Python 层面就不持有可写引用；写入只能经 `Command.redo()`，而"写哪一份"由 Document 的**唯一裁决函数**决定。想写错，得先绕过命令层——那是一处能被静态检查抓住的越界，不是散在几十个函数里的隐性遗漏 | `document.h` 注释原则：任何修改本文档的命令都必须 push 到它的 undoStack |
| **撤销撤一半 / 撤销后画面不刷新**（表象 #4 #10） | `undo()` 与 `redo()` 发出**同一个** `ChangeEvent`；简单命令直接用 `swap()` 模式让两者是**同一个函数**。"正着改能刷新、撤回来不刷新"在物理上写不出来 | `changemapobject.h` 的 `swap()`；`transformmapobjects.cpp` 的 undo/redo 对称 emit |
| **伪脏：点一下就标脏**（表象 #3） | 零变更时**不构造命令**（命令构造函数里比对 before/after，相等即不 push）；"未保存"状态由**撤销游标相对上次保存的位置**推导，不是一个手写的布尔。没有命令 → 没有游标移动 → 没有脏 | Godot 的 `_commit_canvas_item_state`：`old_state.hash() != new_state.hash()` 才建历史项（`editor_node.cpp:393` `_update_unsaved_cache`） |
| **一次拖动 30 条撤销记录**（表象 #5） | `id()` + `mergeWith()` 是命令基类的能力；一次手势里第一帧 `mergeable=False`、之后全 `True`（`std::exchange(mMergeUndo, true)`）。合并是默认行为，不是每个工具自己记得实现的事 | `transformmapobjects.cpp` + `objectselectiontool.cpp` |
| **多选只撤销了一部分** | 多对象变换是**一条命令装一个列表**，不是 N 条命令拼宏。原子性由类型保证，不靠调用者记得配对 | Tiled 明确不用 `beginMacro/endMacro` 做多对象变换 |
| **删除后视图/选择集持已析构对象 → 闪退**（表象 #6） | 成对事件：`MapObjectAboutToBeRemoved` 在指针还活着时广播，所有订阅者拿到"最后一次合法访问"的机会；`Removed` 只用来更新计数 | `changeevents.h` 的 `AboutToBe*` / `*ed` 事件对 |
| **覆盖物抢走点击**（表象 #7） | 命中是**白名单**："只有 `EntityItem` 且 `isEnabled()` 算"。以后再加任何新覆盖物，**默认就不污染命中**，不需要记得去改命中代码 | `abstractobjecttool.cpp` 的命中循环三道过滤 |
| **点不中细小元素 / 双击插点不可达**（表象 #8 #9） | `shape()`（画什么）与 `interactionShape()`（点得到什么）是**两个函数**，后者带视图缩放参数、单位一律屏幕像素。"东西太细点不中"在这里有专门的钩子，不需要在命中代码里塞魔法数 | `src/libtiled/maprenderer.h` 同时声明 `shape()` 与 `interactionShape()` |

**这套架构对本仓不是空降**：`tools/editor/editors/scene_canvas_model.py` 的模块头已经在跟 Tiled 对话（"Tiled 用 `MapObject*` 指针做键……Python 这边没有稳定身份可用"），并且已经用 `PART_TABLE`（`:46`）把"一个实体 = 一束图元"的账本收成唯一真相，把三处手写清单合并成一处。**这张表就是新架构 `SceneMapItem` 的现成子图元账本，直接继承。**

### 2.3 边界拍板：新画布**不**内嵌运行时

这是本方案最重要的一条边界，也是最容易被误解的一条。

**拍板：走 Tiled 路线，不走 Godot 路线。理由三条，逐条附证据。**

1. **Godot 路线的准入前提在本仓不成立。** Godot 之所以"所见即所得是结构上不可能不一致"，是因为编辑器**就是引擎本身**——同一个二进制、同一个进程、同一棵活的节点树（`editor_node.cpp:9020` 把被编辑场景直接 `add_child` 进一个真的 `SubViewport`）。GameDraft 是 **TypeScript 运行时 + PySide 编辑器，跨语言跨进程**。要复刻，得先让编辑器视口跑真 runtime（内嵌 `QWebEngineView`），并让磁盘 JSON 变成"活对象树的投影"（现在是反过来的：JSON 是权威，runtime 与编辑器是两个各自解释它的消费者）。这两条不成立时，照抄 Godot 的技巧只会得到一个**更精致的第二份实现**。

2. **它解决的那个问题，当下的收益被高估。** "在编辑器里看到打完光的结果"这个卖点，实测**29 份场景 JSON 里 28 份有 `lighting` 块、其中 27 份是 `placeholder: true` 恒等占位**（本次实测确认，与 `CLAUDE.md` 记载一致）。也就是说这条卖点今天只对 **1 个场景**成立。

3. **它会把最危险的契约切成跨进程的两半。** 老画布"写当前真相份""press 期抓撤销快照""控件不同步就会反向覆盖"这三条约束，现在是同一个 Python 对象里的同步写；搬到跨进程后变成异步消息——**丢一条 live 消息 = 数据与画面无声劈叉**。而通道的实测延迟是 400–600ms 轮询（`src/dev/runtimeLightingSync.ts:47` / 命令通道 600ms），且编辑器切走别的页时游戏页轮询会被浏览器节流到约每分钟一次。这是整条路线唯一有可能造成**静默数据损坏**的地方，而它换来的是本来就只对 1 个场景成立的收益。

**那"画布骗人"怎么办？——单独立项，走已经在产的那条路，且是单向的。**

`src/authoring/AuthoringMode.ts`（910 行）已经证明了这条路可行，而且它的设计注释就是本方案这条边界的原话：

> "桌面编辑器那边虽然也能摆灯，但那是平面原画上的示意图，看不到打完光的结果。这里摆的每一下都直接在成品画面上。"
> "本模式**不写盘**。摆好的灯留在内存里等编辑器来拉……**工程只能有一个写盘出口**。"
> —— `src/authoring/AuthoringMode.ts:35-46`

**边界怎么切（一句话）：谁拥有写盘和撤销栈，谁就是编辑器；另一侧永远只是显示器。**

- **Qt 侧（新画布）= 作者面（authored space）编辑器。** 只画 JSON 里那一份、只画能拖的东西：锚点、多边形顶点、巡逻折线、深度轴、组框。**主动放弃"所见即所得"**。
- **运行时侧 = 只读预览。** 编辑器改任何东西 → 整份场景数据推给内嵌/弹窗的游戏页 → 约 0.8 秒内画面跟上。**单向、不回写、不进撤销栈。**（灯是唯一的例外，因为它已经反过来了，且已经用 rev + writer 身份 + 新鲜期闸解决了双向问题——不动它。）

这样切的**直接收益**：新画布可以**删掉**三份镜像实现（NPC 精灵世界尺寸、`displayImage` 预览、交互范围圈的透视换算，共约 400–600 行），因为"看着对不对"由真画面回答。**必须保留**的镜像只剩两份——`entity_sort_math.py`（前后遮挡，作者要在画布上排）与 `entity_transform_math.py`（透视系数，拖深度轴时是编辑器自己的交互输入）——而这两份恰好是最便宜的，各自已有钉死的黄金用例（`test_entity_sort_parity.py` ↔ `src/rendering/entitySortRule.test.ts`；`test_perspective_scale_parity.py` ↔ `src/utils/perspectiveScale.test.ts`）。

### 2.4 两个必须现在定的次级决策

**决策 A：撤销命令分两级，不是一刀切。**

- **结构变更**（增/删/复制/重构/分组增删）继续用已有的 `SceneSnapshotCommand`（整场景 `copy.deepcopy`，`scene_undo.py:31`）。它 175 行、与图元实现完全无关、数值往返保真、未知键零丢失——**原样复用**。
- **坐标/几何变更**（拖实体、拖顶点、gizmo、整组平移、方向键微移）新增 `EntityTransformCommand`，对标 Tiled 的 `TransformMapObjects`：一条命令装一个实体列表，带 `id()` + `mergeWith()`，before 在**命令构造时**抓。

这一条直接消灭老画布最贵的一族补丁：`item_drag_press` 信号（`:2424`）、`_on_canvas_drag_press`（`:14778`）、`_drag_undo_before` 状态、`veto_group_gesture`、方向键 400ms idle timer——全部不再需要，因为"before 在哪抓"变成了命令基类的事。

**决策 B：staging 分期处理，MVP 保留但显式建模。**

Tiled 没有 staging——属性面板改一个值就立刻 push 一条命令。这是更干净的形态，也是"commit-on-leave"整族 bug（`CROSS-02` 及 P1-01/P1-25 家族）的根治法。

但 MVP 要复用 6657 行的 `ScenePropertyPanel`（见 §2.5），而它自带 staging。**所以拍板分两期**：

- **MVP 期**：staging 保留，但从"面板私有的第二副本"**升格为 Document 显式的第二层真相**，并提供**唯一裁决函数** `Document.write_target(kind, entity_id) -> dict`。所有命令写入必经它。老画布里 `_group_member_write_dict`（`:13028`）那种"每处手势自己判断写哪份"的写法，变成一行库调用。
- **二期**：把面板的编辑改成即时命令（文本框用 `mergeWith` 合并连续输入），**删掉 staging 与 commit-on-leave 整条链路**。

**这条决策是本方案里唯一的"暂时不彻底"，必须写进计划、必须有二期时间表**，否则 §3.3 的第二个死法就会发生。

### 2.5 最大的既得利益：属性面板确认零耦合

本次实测：**`ScenePropertyPanel`（`scene_editor.py:4582-11238`，6657 行）对画布的引用数 = 0**——在它整个类体内 grep `_canvas` 与 `SceneCanvas`，**零命中**。

它与画布之间只有 **21 条信号**（`:4583-4621`）+ 6 个反向同步入口（`sync_hotspot_xy_widgets:6330` / `sync_npc_xy_widgets:6362` / `sync_transform_widgets:8681` / 三张 `refresh_*_table`）。新画布只要发同名信号、实现这 6 个入口，**面板一行不改就能接上**。

同样零改动复用的还有：`ProjectModel`（2487 行）、`scene_undo.py`（175 行）、`scene_canvas_model.py`（97 行）、`scene_lights.py`（900 行）、`entity_sort_math.py`（291 行）、`entity_transform_math.py`（239 行）、`entity_refactor.py` 与对话框（2540 行）、全部 shared 选择器控件。

**换算成人话：老文件 16037 行里，真正需要重写的是 6490 行（40.5%），其余 9547 行确认可原样接。**

## 三、诚实的反方意见

### 3.1 这个架构解决不了什么（五条，逐条承认）

1. **"画布骗人"完全不治。** Tiled 没有这个问题，因为它画的瓦片和对象**就是**游戏加载的那一份，画布即真相。GameDraft 的画布画的是 PixiJS 2.5D 渲染器的一个**近似**。换架构与这件事**正交**。这也正是 §2.3 要把它切出去单独立项的原因。

2. **Qt 事件栈里改布局仍会段错误。** 老画布满仓的 `QTimer.singleShot(0, self, ...)` 不是历史包袱，是 QGraphicsView 的固有约束：在鼠标事件派发栈中间装载面板 → 布局重排 → 画布 resize → `fit` 的 `resetTransform()` → **实测 SIGSEGV**（`_SceneGroupBox.mousePressEvent` `:2265-2322` 的注释记录了这个死法）。新架构把"press 阶段只做画布内的事"变成了一条更容易遵守的纪律（因为 Command 的提交本来就在 release），但**不会自动执行它**。

3. **命中尺寸的单位仍要人写对。** `interactionShape` 给了正确的地方放这段逻辑，但不给正确答案。"世界单位 14 在 fit 后缩成 3 像素"这个错误，在新架构里照样写得出来。

4. **跨文件重构仍然不能进撤销栈。** `entity_refactor` 改写的是整个项目的引用网（多文件状态），场景级命令跨过它做撤销会产生半份回退。所以执行后仍必须清栈（`scene_undo.py:172` `clear()`），回退只能用重构自己的 journal。这条 Tiled 也一样（它的跨文件操作同样不在地图的 undoStack 里）。

5. **"提示写着能做、实际做不到"这类 bug 不会被自动发现。** 双击插点不可达之所以长期没人发现，是因为**没有任何交互级测试**覆盖画布的双击/右键路径。新架构给了可测的接缝（Tool 可以脱离 Qt 单测），但**测试要人去写**。

### 3.2 它自己会引入什么新问题（四条）

1. **样板税，且是永久的。** 每个操作一个命令类。这是这套架构唯一无法用工具消除的成本，也是团队最容易绕过去的地方。Tiled 自己的 `undocommands.h` 里登记了 **40+ 个命令 ID**，那就是这笔税的账单。

2. **变更事件的粒度是新的设计难题。** 太粗（"场景变了"）→ 每次改动全量重建视图，性能塌方 + 选择态丢失；太细 → 回到"漏发一条就不同步"。Tiled 自己**至今没迁完**——它同时保留着老式的逐信号（`selectedObjectsChanged`、`layerAdded`…）与新式 `changed(ChangeEvent)` 两套，是明确的历史包袱。**本方案的应对：只做 `ChangeEvent` 一套，不复制这个二元性**；粒度按 Tiled 的 `properties` 位掩码走（订阅者能判断"只是位置变了"→ 只 `setPos()`，不重建几何）。

3. **push 模式要付"信号无遗漏"的税。** 这是 push（精确通知）相对 pull（每帧重算）的固有代价。React/Flutter 选 pull 是因为"重算一次不贵"；编辑器场景对象（贴图、精灵、GPU 资源）重算贵，所以必须 push。判据只有一条：**重算贵不贵**。本方案在 overlay 层（选中框/标签/手柄）用 pull（即时重画，`prepareGeometryChange` 只在包围盒真变时调），在实体图元层用 push。

4. **双画布并存期的三个死法**（详见 §5.2）：staging 幽灵覆盖、两个撤销栈互撤、导航路由 first-wins。这三条**必须在写第一行画布代码之前解决**。

### 3.3 业界为什么有人不这么做

- **成本不划算。** 一次性重写 + 永久样板税，对一个只有几百行的小工具是明显亏本的。老画布刚开始的时候是对的选择——错在它长到 16000 行还没换。
- **有人认为即时模式够了。** Unity（`OnDrawGizmos` / `Handles`）、Unreal（`FEdMode::Render` + `PDI`，画出去的东西**不返回句柄**、不可寻址）、Dear ImGui 都把 overlay 做成每帧重画。**但注意：他们只把即时模式用在 overlay，数据侧仍然是命令/事务**（UE 的 `FToolCommandChange` 有 `Apply()`/`Revert()`，Unity 有 `Undo.RecordObject`）。所以"即时模式"与"命令模型"**不是对立选项，是不同的层**。本方案两者都用，各在其位。
- **Godot 派整个绕开了这个问题。** 编辑器就是引擎，真相就是内存里那棵活的节点树，磁盘 `.tscn` 只是它的 dump（`editor_node.cpp:2512` `sdata->pack(scene)`）。它连 Document 这一层都不需要。我们做不到（跨语言），所以不能照抄。
- **有的工具直接不做撤销**，或用整文件快照（我们已经在用，`scene_undo.py`）。整文件快照对小数据是完全正确的工程选择——本方案保留它，只在坐标/几何这一族叠加细粒度命令。

### 3.4 如果这次重写失败，最可能死在哪一步

按概率排序，附各自的止损点：

**死法一（概率最高）：死在"两个画布并存期"。**
老画布还在用、新画布只覆盖最小集，用户被迫来回切；每切一次，就有一次机会触发 staging 幽灵覆盖或两个撤销栈互撤（§5.2）。表现是"用了新画布之后数据反而更容易坏"，一次事故就足以让方案被否掉。
**止损**：§5.1 的 Step 0 四项前置**必须先于任何画布代码**，且各自有独立验收。做不完 Step 0 就不许开工写画布。

**死法二：死在"面板不肯改"。**
MVP 复用 6657 行面板 = 继承 staging。如果只是"把 staging 原样搬过去"而没有把它建模成 Document 的显式第二层 + 唯一裁决函数（决策 B），那么新架构会在第一个"整组平移写错副本"上**原样复现老 bug**，然后所有人得出"换架构没用"的结论——而实际上失败的是没执行决策 B。
**止损**：`Document.write_target()` 必须是 Step 1 骨架的第一个函数，且必须有单测覆盖"实体正被面板打开时写 staging、否则写模型"这两条分支。

**死法三：死在"样板税"。**
第 3 个月，有人为了赶工在 Tool 里直接写了一行 `ent["x"] = new_x`，代码评审放过去了。半年后新画布退化成老画布，只是文件名不一样。
**止损**：一条 CI 静态检查——**新画布的 `tools/` 与 `items/` 目录里禁止对场景 dict 做下标赋值**（AST 扫描，几十行）。这比任何文档、任何 review checklist 都管用，因为它不依赖人的记性。这条检查本身就是"根因不再是口头约定"的物证。

## 五、迁移路径

### 5.1 单一真相的定义（先说清楚，后面每一步都靠它）

- **唯一权威**：`ProjectModel.scenes[sid]`（`project_model.py:90`），场景 JSON 的裸 dict。新老画布共享**同一个** `ProjectModel` 实例。
- **唯一写盘出口**：`ProjectModel.save_all()`（`:858`）。运行时永远不写盘。
- **唯一撤销栈（每场景一条）**：`SceneUndoController.stack`。
- **第二层真相（MVP 期）**：staging。裁决权归 `Document.write_target()`，**任何代码不得自行判断写哪一份**。

### 6.2 三大风险与缓解

**风险一：并存期的数据事故（概率高 · 后果严重 · 不可逆）**
两份 staging 指向同一个模型 dict、两个撤销栈持同一场景的快照。表现是"用了新画布之后数据反而更容易坏"——一次事故就能否掉整个方案。
**缓解（三条，全部可独立验收）**：① Step 0-d 的激活期 `reload_from_model()` + `notice_external_scene_write` 跨 page 广播，**先于任何画布代码**；② Step 0-c 的导航开关保证同一时刻只有一个画布可被导航到；③ 并存期给 `ProjectModel.save_all()` 加一条一次性自检：落盘前对比"本次写出的场景 JSON"与"上次读入 + 已知命令序列的预期"，不一致就拒绝落盘并报出差异（约 80 行，只在并存期开启）。
**残余风险**：③ 只能挡住结构性差异，挡不住语义正确但不是用户想要的写入。可接受。

**风险二：架构被绕过、半年后退化（概率中高 · 后果 = 全部投入归零）**
样板税是这套架构唯一无法用工具消除的成本，也是最容易被赶工绕过的地方。老画布本身就是这么长出来的。
**缓解**：一条 CI 静态检查——`scene_v2/tools/` 与 `scene_v2/items/` 目录里**禁止对场景 dict 做下标赋值**（AST 扫描 `Subscript` 形式的 `Assign` 目标，几十行）。同时把这条检查连同"写入必经 `write_target()`"写进 `agent_docs/editor-tools/norms.md`，但**以 CI 为准、文档为辅**——因为文档不阻止提交，CI 阻止。
**残余风险**：静态检查可以被 `setattr` 之类的动态写法绕过。可接受（绕过要刻意，且会在 review 里显眼）。

**风险三：把"画布骗人"捆进这次重写（概率中 · 后果 = 工期翻倍且两件事都做不成）**
这是最隐蔽的一条。一旦开会时有人说"既然都要重写了，不如顺便把预览做真"，工期就从 2.5 人月变成 6–8 人月，且要跨 TypeScript / Python / Vite 三处，把最危险的 staging 契约切成跨进程异步两半。
**缓解**：① 本方案 §2.3 已经把边界写成一句可以贴在墙上的话——**谁拥有写盘和撤销栈，谁就是编辑器；另一侧永远只是显示器**；② 预览做成**独立的并行轨道**，有自己的 2–3 周预算、自己的验收（"编辑器改一个热点坐标，右侧游戏画面 1 秒内跟上"），**不进新画布的任何代码路径**；③ 预览轨道**单向**，MVP 期不做任何回流。
**残余风险**：单向预览意味着"在真画面里看着不对，还得回编辑器改"——多一次来回。可接受，且这正是 `AuthoringMode` 已经在灯上验证过的形态（它也不写盘，只等编辑器来拉）。

### 6.3 拍板汇总（可被反驳的六条结论）

1. **根因是"没有唯一写入口"**，不是"bug 多"。证据：`scene_editor.py:14723-14734` 的两级手写脏标记、`:13028` 的逐成员写入目标判断、29 条画布信号 × 81 个公共方法的分散写入面。
2. **采用 Document–View–Command（Tiled / Qt Undo Framework），技术栈保持 Qt。** 不采用 Godot 式内嵌运行时当画布——因为它的准入前提（编辑器即运行时、磁盘格式是活对象树的投影）在本仓不成立，且其核心卖点当下只对 29 个场景中的 1 个成立（实测 `placeholder: true` 27/28）。
3. **"画布骗人"单独立项，走单向只读预览**，复用 `src/authoring` 与 `runtimeLightingSync` 已验证的形态。边界：写盘与撤销栈的所有者只有 Qt 侧。
4. **MVP = 选/拖/增/删 + Zone 多边形 + 巡逻折线 + 撤销 + 脏标记 + 树联动 + 视图过滤。** 分组（实测仅 3 个）、变换手柄（实测 `rotation≠0` 的实体为 0）、透视轴（3 个场景）、光曲线（1 个场景）全部进二期/三期。
5. **staging 分期处理**：MVP 保留但升格为 Document 显式第二层 + 唯一裁决函数；二期随面板改造一并删除。这是本方案唯一的"暂时不彻底"，已列入 Step 5。
6. **Step 0 的四项前置必须先于任何画布代码**，否则最可能的死法（并存期数据事故）会在第一周发生。
