## 一、存量债（与本次探索无关，先于它存在）

### 1. 主线是断的 —— 最要紧

`public/assets/data/narrative_graphs.json` 里 `flow_xungou_main` 的开局被重接过，现在是：

```
state_1 --[reactive: GameConfig_Demo主线剧情]--> initial
        --[主线_开局被赶出茶馆]--> state_2
        --[reactive: wrapper_主线_崖墓任务发布 到 state_2]--> state_3
        --[__draft__]--> s02_beishi        ← 这一跳永远走不了
```

`t_4` 挂的是 `__draft__`（草稿占位信号），`NarrativeStateManager.emitNarrativeSignal` 里有硬拦截，
**永远不可能被发出**；而 `t_4` 是**唯一**通向 `s02_beishi`（背尸）的边。

**结论：主线走到 `state_3` 就死在那里，demo 开局过不去。** 需要作者补一个真实信号名。

校验器一直在报，被忽略了：
```
[WARN] [narrative] flow_xungou_main: Transition 't_4' 仍是草稿信号 __draft__（不会被任何来源触发）
```
同类还有两条 signal 型：`癞子NPC.t_2`、`wrapper_graph_1.t_1`（后者整张图是编辑器脚手架残留，
label「棺材铺门口」，states 还叫 `initial`/`state_1`）。另有 6 条挂 `__draft__` 的是 `reactive*` 型，
signal 字段本就不读，**无害**。

## 二、「实例 wrapper」评估结论（探索已 revert，结论留下）

### 为什么放弃

原始诉求是「1000 个箱子各有各的状态，不想要 1000 个信号名 / 1000 张图」。
实现了一版「原型 + 绑定即实例化」后复盘，**运行时什么也没买到**：

- 1000 张独立图全监听同一条信号，**今天就能跑，零新代码**；
- 每条信号的扫描成本，1000 张图与 1000 个实例**同为 O(N)**（除非做群体合并，而那没做）；
- 存档条目数一样；
- 灵活性上 1000 张独立图**更强**（每个箱子可以长得不一样）。

唯一买到的是「不必写 1000 张同构图」，而编辑器已有模板盖章机制。
**结论：没做群体合并的实例化 ≈ 模板盖章 + 一堆新概念和新失效模式。**

且本项目现网 55 张图（28 张是两状态 wrapper），1000 个箱子是假设不是需求。

### 若将来真要做，正确的做法

不是「每实例一条记录」，而是 **retained message / log compaction 那一族**：
每个原型保留一条「未分化实例的当前状态」（群体记录，常驻），
被玩家单独操作过的实例才裂出独立条目。

- 未加载实例天然收得到信号（群体是接收方），无保留窗口、离线多久都不丢；
- 条件在信号发生**那一刻**求值一次、作用于整个群体，不存在补判时的条件漂移；
- 存档 = 每原型一条 + 被碰过的那几个。

**成立前提**：同一原型的未分化实例对同一信号反应必然一致 ⇒ 转移条件只能读世界状态与实例自身变量，
不能读实例身份/宿主场景。现有条件叶天然满足，但加身份类叶子会悄悄打碎它。

### 走过的弯路（别再走）

**用了错误的模式族**：先做的是 durable subscription + 回放游标（信号台账 + 每实例 cursor +
保留窗口）。那一族适合**事件流**；叙事状态是**状态**（只关心当前值），该用 compaction 族。
族选错的后果是修完一个冒一个：重数丢失、条件按补判时刻求值而漂移、
「档里缺席」同时意味着出厂态与未出生的两义冲突、保留窗口溢出。

**边沿触发 vs 电平触发**是判据：`reactive` 转移是电平触发，对加卸载天然免疫
（加载时重算条件即可，无需记住错过了什么）；信号是边沿触发，才有「不在场就漏」的问题。
**能用条件表达的一律用 reactive**，这是最省事的一条。

**私有性做过头**：曾把实例状态设计成连宿主实体自己都读不到，导致实体显隐只能靠动作写全局 flag——
恰好把要消灭的命名膨胀原样请了回来。项目里 `ownerState` 节点与 `@owner` token
**本来就是**「读我所属实体的状态图」这个机制，不该另造。

## 三、保留下来的需求（转入后续轮次）

**私有信号**：1000 个箱子共用一张对话图发同一个信号名，按发射方 owner 定向投递给它自己的
wrapper 图。这是本次探索里唯一真正缺失、且用现有机制补得干净的东西——
`actionOrigin` 已在线程化 owner，`getGraphIdsByOwner` 已能映射，改动只在投递处收窄候选 + 三条校验。

**编辑器批量盖章**：入口应在场景编辑器（摆箱子时顺手绑），多选实体 → 应用模板 →
批量生成 wrapper 图，id/ownerId 从实体推导。配套需要画布分组折叠，
否则 100 张图铺开会淹掉画布——「能创建」和「能看」同等重要。
