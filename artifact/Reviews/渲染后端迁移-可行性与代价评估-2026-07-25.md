# 渲染后端迁移 —— 可行性与代价评估

> 日期：2026-07-25　｜　范围：`src/`（54,017 行非测试 TS）+ 共用 shader 的工具链
> 触发：现有 Pixi 抽象与 3D 图形学心智模型持续错配，带来不可接受的认知负担
> 性质：**只评估，不动手**。给数字、给边界、给取舍，不给既定结论

---

## 0. 结论先行

1. **认知负担是真问题，不是不适应。** Pixi 没有"材质"这个概念。想给 sprite 自定义着色，官方唯一路径是 Filter —— 而 Filter 是**屏幕空间后处理**。项目实际要做的是**几何空间的材质着色**。这两件事在 Pixi 里被强行等同，代码里每一处 hack 都是这个错配的产物（见 §1 对照表）。

2. **世界渲染层是一块干净可切的薄片：7,216 行，占 src 的 13%。** 且迁移账本远比预期便宜——世界层**零 Pixi 事件依赖**，帧切分是自研的，资源加载只有 1 处 `Assets.load`。

3. **最大成本不在渲染层，在 UI 层（9,087 行 / 32 文件手搓 Pixi 控件）。** 但 UI 与本次决策**正交**——认知负担 100% 来自世界层。**不要把 UI 迁移绑进这个决策**，否则 7,216 行的活会被 9,087 行的活拖死。

4. **推荐：世界层迁 three.js，UI 层原样留在 Pixi 叠层。** 9 个 shader 的 GLSL ES 3.00 可原样复用（含与灯光实验室的共享真相源契约），`sampler3D` / MRT / WebGPU 三个当前封死的能力同时解锁。

5. **有一条更便宜的中间路必须先摆上台面**：不换后端，只把逐实体 Filter 改成 **Mesh + Shader**。这能拿回约 80% 的心智模型（Pixi 的 `Mesh` 是真顶点管线），代价约为迁移方案的 1/4。但 `sampler3D`、MRT、WebGPU 仍然封死。**如果你的诉求主要是"别再让我用 filter 思考"，这条路可能就够了。**

## 1. 认知负担的机制：概念对照表

这张表是本文的核心。左列是你的心智模型，右列是 Pixi 的实际情况——**每一行的错配，都在代码里留下了具体伤痕**。

| 3D 管线概念 | Pixi 里的对应物 | 错配后果（附证据） |
|---|---|---|
| **Mesh + Material** | **不存在材质概念。** `Sprite` 是固定管线 quad。自定义着色的唯一官方路径是 `Filter` | Filter 活在屏幕空间，被迫在后处理里**重建模型空间** |
| **VS 拿顶点属性**（UV / 法线 / 模型矩阵） | Filter 的 VS 只有全屏 quad 的 `aPosition`，且**会被屏幕裁剪** | `uSpriteWorldRect` uniform 反推世界坐标。[CharacterShadingFilter.ts:112](../../src/rendering/CharacterShadingFilter.ts) 注释是实测血书："半出屏的 NPC 整个变饱和纯绿" |
| **Draw call / 批处理** | 挂 filter 即**脱批**：单独渲到 RT 再 blit 回来 | `雾津街头` 36 实体 = 36 次 RT 分配 + blit / 帧，批处理彻底断开 |
| **Render pass / RenderTarget 编排** | `FilterSystem` 自动 push/pop，**你不控制** | 无法编排 G-buffer / MRT。`DeferredEntityShadow` 是自己搭的，不是引擎能力 |
| **`sampler3D`** | **不存在** | 体素卷拍成 Z 切片平铺 2D 图集 + [手写三线性插值](../../src/rendering/CharacterShadingFilter.ts) |
| **Uniform buffer / 描述符集** | `uniforms` 对象 + BindGroup，**所绑资源一销毁整个 BindGroup 自毁** | 换资源必须"先重挂滤镜、再销毁旧纹理"的时序硬约束。[Game.ts:3133](../../src/core/Game.ts)、[BackgroundDebugFilter.ts:206](../../src/rendering/BackgroundDebugFilter.ts) |
| **材质状态切换** | `filters` setter 每次赋值都 slice + freeze + 重建 `FilterEffect` | 只允许在启用/禁用边界切换。[SpriteEntity.ts:106](../../src/rendering/SpriteEntity.ts) |
| **WebGPU / compute** | 自定义 shader 一律走 `GlProgram`（**WebGL-only**） | **6 处 `new GlProgram`，0 处 `gpuProgram`/WGSL** → WebGPU 后端完全封死 |
| **上下文生命周期** | `Application.destroy` 在 HMR / 重复卸载下不可靠 | [Renderer.destroy](../../src/rendering/Renderer.ts) 三层 try/catch + 手动断 `resizeTo`；连 `screenWidth` getter 都要 try/catch 兜底 |

**一句话总结**：Pixi 是"2D 批渲染器 + 逐对象后处理滤镜框架"。项目实际需要的是"逐实体材质 + 场景级辐照度探针 + 深度遮挡 + 投影阴影"，也就是一个前向/延迟 3D 渲染器。**不是 Pixi 做得不好，是拿它当渲染器用本身是越界。**

### 需要澄清的一点

代码里的 `for(int i=0;i<192;i++)` 套 `for(int s=0;s<256;s++)` 实时 RT gather **不在生产路径上**。默认 `uMode: 2`（L2 probe，纯 `texelFetch`），RT 是 F2 里的对比档。所以当前性能瓶颈是 **pass 数**，不是每像素步进。

## 2. 迁移账本（实测）

### 2.1 世界渲染层 —— 迁移标的

| 项 | 规模 | 迁移难度 |
|---|---|---|
| `src/rendering/*.ts`（23 文件） | 5,766 行 | 中 |
| `core/CharacterLightingSystem.ts` | 900 行 | 中（**本就是渲染系统，错放在 core/**）|
| `core/SceneDepthSystem.ts` | 544 行 | 中（同上）|
| **合计** | **7,216 行 = src 的 13%** | |

其中 `CutsceneRenderer.ts` 一家占 1,291 行，但只用 `Container`/`Sprite`/`Graphics`/`Text`/`alpha`——**零 `blendMode`、零 `mask`**，迁移直白。

### 2.2 Shader 清单（9 个 GLSL ES 3.00）

| shader | 用途 |
|---|---|
| `charShadeCore.glsl` | **共享真相源**：`shadeCharacterLinear` |
| `CharacterShadingFilter` | 逐像素角色着色（probe/SH/伪世界照明）|
| `DepthOcclusionFilter` | 深度遮挡 |
| `EntityLightingFilter` | 逐实体光照（旧色调管线 fallback）|
| `EntityShadow` / `DeferredEntityShadow` | planar 剪影 / 投影阴影 |
| `overlayBlendShader` | 叠图混合 mesh |
| `BackgroundDebugFilter` | 背景调试 |
| `WaterShaderFilter` / `WaterParamEncodeFilter` | 小游戏水面 |

**关键情报**：灯光实验室 [`tools/character_lighting_lab/viewer/app.js`](../../tools/character_lighting_lab/viewer/app.js)（3,203 行）是**原生 WebGL**（307 处 `gl.*` 调用），不是 Pixi。`serve.py:279` 把 `src/rendering/charShadeCore.glsl` 注入实验室，实现"实验室调的参数到游戏里就是对的"这条契约。

→ **选 GLSL 后端（three.js / 原生 WebGL2）：shader 原样复用，契约零影响。**
→ **选 WGSL-only 后端：契约断裂，实验室要跟着重写 3,203 行。这是硬成本。**

### 2.3 意外便宜的三项

| 项 | 实测 | 结论 |
|---|---|---|
| **世界层交互** | `entities/` + `rendering/` 里 `eventMode`/`hitArea`/`pointer` 事件 **合计 1 处**（且是 `eventMode='none'`）。交互靠 [InteractionSystem](../../src/systems/InteractionSystem.ts) 的距离/多边形判定 | **零成本** |
| **资源加载** | 全项目 `Assets.load` **1 处**、`Spritesheet` **0 处** | **近零成本** |
| **动画帧切分** | 自研：共享 `texture.source` + `new Rectangle` 子矩形（[SpriteEntity.ts:142](../../src/rendering/SpriteEntity.ts)），`anim.json` 自有契约 | **近零成本** |

这三项本来是 2D 引擎迁移的典型泥潭，这个项目恰好全都自己实现了。

### 2.4 成本集中处

| 项 | 规模 | 说明 |
|---|---|---|
| **UI 层** | **9,087 行 / 32 文件** | 121 `new Text` + 107 `new Graphics` + 41 `eventMode` + 56 pointer handler + 19 `hitArea`。无布局系统，`PanelSkin` 是唯一共享抽象 |
| **小游戏** | water 1,889 / sugarWheel 2,731 / paperCraft 828 | 自带 2 个 shader + Pixi 事件依赖，是 `systems/` 里唯一的 Pixi 事件用户 |

**能力面按层切分**（决定混合方案可行性）：

| 能力 | ui/ | systems/ | rendering/ | entities/ |
|---|---|---|---|---|
| `new Text` | 121 | 28 | 5 | 3 |
| `new Graphics` | 107 | 35 | 16 | 3 |
| `eventMode` | 41 | 41 | 1 | 0 |
| `.on('pointer` | 56 | 37 | 0 | 0 |
| `hitArea` | 19 | 8 | 0 | 0 |
| `MeshGeometry` | 0 | 0 | **11** | 0 |
| `RenderTexture` | 0 | 5 | **9** | 2 |

**切割线极其干净**：GPU 实际工作（Mesh/RenderTexture）全在 `rendering/`；文本与事件全在 `ui/` + 小游戏。**世界层和 UI 层在 Pixi 依赖上几乎不重叠。**

## 3. 候选后端

| 后端 | 心智模型契合 | GLSL 复用 | `sampler3D` | MRT | WebGPU | UI/中文文本 | 综合 |
|---|---|---|---|---|---|---|---|
| **three.js** | **1:1**（Mesh/Material/Pass/Camera 全对应）| ✅ 原样 | ✅ `Data3DTexture` | ✅ | ✅ `WebGPURenderer` 可选 | ❌ 无 UI 系统 | **最优** |
| **原生 WebGL2** | **1:1**，零抽象错配 | ✅ 原样 | ✅ | ✅ | ❌ | ❌ | 控制最强，自造轮子最多 |
| **Babylon.js** | 高 | ✅ | ✅ | ✅ | ✅ | ⚠ 有 GUI 但偏 3D-first | 更重，2.5D 用起来别扭 |
| **Pixi + Mesh/Shader** | 约 80% | ✅ 原样 | ❌ | ❌ | ❌ | ✅ 现状不动 | **中间路，见 §4-B** |
| **Pixi 现状** | 低（本文起因）| — | ❌ | ❌ | ❌ | ✅ | 基准线 |

**关于 three.js 无 UI 系统**：这不是问题，因为按 §2.4 的切割线，**UI 可以整块留在 Pixi**。two-canvas 叠层：three canvas 渲世界，Pixi canvas 渲 UI，z-index 叠放。`uiLayer` 本来就已经是独立于 `worldContainer` 的顶层容器（[Renderer.ts:76](../../src/rendering/Renderer.ts)），拆分点天然存在。

代价：两个 WebGL context（显存与 context 切换开销，现代浏览器可接受）；`cutsceneOverlay` 需要决定归属（它介于世界与 UI 之间，建议跟 world 走，因为要吃世界滤镜与相机）。

## 4. 三条路径与代价

### A. 只做渲染层归位重构（不换后端）

把 `CharacterLightingSystem` / `SceneDepthSystem` 移出 `core/`（顺带修铁律 1 违规），抽一个 `EntityShadingPipeline` 拥有逐实体滤镜生命周期，Game.ts 退回纯 wiring，删掉 `rendering/filter/` 那个只支持 ColorMatrix 的空壳抽象。

- **代价**：小。约 7,216 行内部搬迁 + Game.ts 减重
- **收益**：装配层有主、不再恶化
- **不解决**：**认知负担一分不减**。你还是在用 filter 思考
- **判断**：**必要但不充分**。B 和 C 都应包含它

### B. 保留 Pixi，逐实体 Filter → Mesh + Shader（中间路）

Pixi 的 `Mesh` + `GlProgram` **是真顶点管线**：自定义 geometry attributes、自己的 VS、不走 FilterSystem 的离屏 pass。项目已经在用（`MeshGeometry` 11 处、`overlayBlendShader`）。把角色着色从 Filter 改成挂在实体 quad 上的 Mesh material：

- **代价**：A 的成本 + 重写 5 个 filter 为 mesh material（GLSL 主体复用，改的是 VS 与 uniform 注入方式）
- **收益**：
  - 拿回批处理，逐实体离屏 pass 消失
  - `uSpriteWorldRect` 那类 hack **自然消失**（顶点属性直接给你模型空间）
  - **心智模型回到 Mesh + Material + Shader**，约 80% 的认知负担消除
- **不解决**：`sampler3D`（体素卷仍要平铺 hack）、MRT/G-buffer、WebGPU
- **判断**：**如果诉求主要是"别再用 filter 思考"，这条路性价比最高。约为 C 的 1/4 成本。**

> **⚠ 现场更新（2026-07-25 11:05，本文写成后发现）**
> 本仓库存在**并行写入者**，正在实施的就是 B：新增未跟踪文件
> `src/rendering/CharacterLitSprite.ts`（322 行，Mesh + `GlProgram` + 顶点自带图集 UV），
> `core/CharacterLightingSystem.ts:16` 已 import，集成进行中；
> `CharacterShadingFilter.ts` 已抽出 `CHAR_LIGHT_COMMON_GLSL` 供 filter 与 mesh 共用。
> 该文件头部注释披露了一条**本文低估的事实**：filter 路径的缺陷不止性能与认知负担，
> 而是**正确性事故**——filter 拿不到图集 UV（Pixi 画 sprite 时用完即弃），旧路径被迫
> 从世界坐标反推法线 UV 并逐帧 CPU 驱动；**任何一帧驱动缺席**（实测：非 Exploring 态
> 整段驱动被跳过）→ UV 整体越界被 clamp 死在 0/1 → 全身反复采同一列边缘像素：
> **通体单色、镜像后换一列（绿↔黄）、随 uniform 跳变闪烁**。
> 这正是 §1 表格第 2 行"VS 拿不到顶点属性"的错配后果，且比 `uSpriteWorldRect` 那处更严重。
> **修正判断**：B 不只是"降低认知负担"的性价比选项，它同时消除一整类结构性错位
> （"没有任何逐实体逐帧 CPU 驱动 → 这类错位在结构上不再存在"）。
> 深度遮挡仍留在 `DepthOcclusionFilter`——**那是 filter 的正当用途**（屏幕空间后处理）。

### C. 世界层迁 three.js，UI 留 Pixi（推荐）

- **代价**（按 §2 账本）：
  - 世界层 7,216 行重写，**9 个 shader 的 GLSL 原样复用**
  - 相机/资源/剔除映射：`Camera.ts` 220 行 → three 正交相机；`AssetManager` 纹理面仅 1 处 `Assets.load`
  - `CutsceneRenderer` 1,291 行迁移（无 blendMode/mask，直白）
  - 世界层交互 **零改动**（几何判定与渲染无关）
  - 帧切分 **近零改动**（自研 Rectangle 子矩形 → three 的 UV offset/repeat）
  - two-canvas 叠层接线 + `cutsceneOverlay` 归属决策
  - **UI 层 9,087 行零改动**，小游戏 5,448 行零改动（留在 Pixi canvas）
- **收益**：
  - 心智模型 100% 对齐，认知负担归零
  - `sampler3D` 解锁 → 体素卷平铺 hack 与手写三线性可删
  - MRT/G-buffer 解锁 → 延迟着色、真正的多光源、后处理链可做
  - WebGPU 路径打开（GLSL 走 WebGL2，未来可选 TSL/WGSL）
  - 灯光实验室契约保持（同为 GLSL）
- **风险**：
  - 两个 WebGL context 的显存与切换开销
  - 迁移期双渲染路径并存，需要视觉一致性门禁（项目已有无头截图验证配方可复用）
  - `EntityPixelDensityMatch`、`irradianceProbe`（用 Pixi RenderTexture + BlurFilter 烘焙）要重做
- **判断**：**认知负担与技术天花板一次性解决，且账本比直觉便宜得多。**

### 明确不推荐

- **整体（含 UI）迁 three.js**：UI 9,087 行手搓控件在 three 里无处安放，成本翻倍且收益为零
- **WGSL-only 自研后端**：打断与灯光实验室的共享 GLSL 契约，实验室 3,203 行要跟着重写

## 5. 推荐路线

**A → B → C 是严格递进的，且 A 是 B/C 的公共前置。**

建议分两步决策：

1. **先做 A（渲染层归位）**。无论最终换不换后端都必须做，且做完之后 B/C 的迁移面会清晰得多——现在 Game.ts 拥有渲染装配，不先收口，迁到任何后端它照样会拥有。

2. **A 做完再定 B 还是 C**，判据是单一的：
   - 如果诉求止于**"别再用 filter 思考"** → **B**（1/4 成本拿 80% 收益）
   - 如果还要**真 3D 纹理 / G-buffer / 多光源延迟着色 / WebGPU** → **C**

**如果现在就要押注**：选 C。因为按 §2 账本，C 相对 B 的**增量**成本主要是"换库"这一次性开销，而 §1 表里 `sampler3D`/MRT/WebGPU 三行是 B 永远解不开的死结——以这个项目在角色照明上的投入强度（伪世界照明、SH probe、体素卷、光源驱动阴影），撞上这三条只是时间问题。

### 5.1 现场修正：B 已在实施中（2026-07-25 11:05）

发现并行写入者正在实施 B（见 §4-B 的现场更新），据此修正路线：

1. **A 不能在此刻动手。** A 的标的（`CharacterLightingSystem`、`Game.ts` 逐实体着色装配）
   与 B 的在施工面**完全重叠**。两个写入者同时改这几个文件必然互毁。
   **A 必须等 B 的这一批集成落地（tsc 绿）之后再启动。**
2. **A 的内容需按 B 的落点重算。** B 把逐实体着色从 filter 搬到 Mesh 之后：
   - `CharacterShadingFilter` 从主路径降级为 fallback，逐实体 filter 的生命周期管理面缩小；
   - "逐帧 CPU 驱动 uniform"这一整块（`driveBakedShading` / `driveFilter`）**结构性消失**，
     Game.ts 的减重量比本文估算的更大；
   - `EntityShadingPipeline` 的所有者边界应按 `CharacterLitSprite` 的挂载点重新划，
     而不是按现在的 filter 挂载点。
   → **A 的方案应在 B 落地后重新出，不要照搬本文 §4-A。**
3. **B 落地后 C 的账本要重新核。** B 把世界层从"filter 后处理"搬到"Mesh + 顶点管线"，
   这恰好是 three.js 的原生形态——**迁移面会显著变小**，§2.1 的 7,216 行里可直接映射的
   比例上升。C 的成本估算应在 B 完成后重算，届时 C 的性价比只会更好。
