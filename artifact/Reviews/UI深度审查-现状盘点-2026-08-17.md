## ① TL;DR：离商业作品差在哪

1. **底子不烂，缺的是"件"不是"功"**：皮肤/令牌/窗体/滚动/焦点五件套真实收口过、坑都踩过并留了注释，定稿美学在皮肤层完整落地（title.png 的海报页、shop.png 的木框面板都成立）。
2. **"文字没有重点"的根因在令牌层**：字号七档有纪律，颜色零纪律——约 14 档近邻暖灰无语义映射（UITheme.ts:53-146），全站层级只剩"琥珀 vs 一片灰"一条对比轴；册子正文更是把印象/例句/来源/备注全拍平成一种字号一种颜色（ArchiveBookView.ts:450-456）。
3. **"导航逻辑乱"的根因在架构层**：桌面端 7 个内容面板零可见入口零键位教学（P0）；UI 开关四范式并存、Esc 在相邻语境有 5 种语义、顶中 100px 挤 4 个通知通道无仲裁。
4. **"表现逻辑乱"的根因是组件层没有任何布局原语**（栈/网格/分栏/页签全无），30+ 面板各自手写坐标，同为左右栏各画各的（P0）。
5. **收集册图文排版真实上限**：单栏竖排 + ≤200px 高贴左横图，仅 [img:] 一个标记——是"能塞图的纯文本"不是"图文排版"，且皮肤层连亮底纸页材质都没有；人物簿数据层连图片字段都没有。
6. **"标记词条可点击采集"距离 = 一个中型系统**：作者侧标记管线/校验/打字机安全截断已就绪（约六成地基白捡），但全部文本渲染进单个 Pixi Text、无 span 几何、无线索数据模型——渲染命中层与玩法数据层为零。
7. 幸运的是：图文排版升级与可点击词条是**同一笔投资**（RichContent 升级成 run 级小版式引擎），令牌灰域收敛是**低成本高回报**的第一刀。
8. 另有一条发行阻断项：DevModeUI 仅靠 `?mode=dev` 门控、生产构建可达（main.ts:9; Game.ts:2184）。

## ③ 六大横切问题（按 category，P0→P2）

### navigation（导航/入口/焦点）

- **P0 桌面端面板系统零入口可见 + 零键位教学**。7 个内容面板（任务/行囊/规矩/对话录/书架/地图/用规矩）只能背 Tab/I/R/L/B/M/G，HUD 无按钮、无帮助页、设置页无键位表；触屏端反而有全套 10 按钮——同一游戏两套信息架构，桌面盲、触屏挡。hud.png 实拍可证：画面上除铜钱/香火/场景名外无任何入口。证据：HUD.ts:19-24; Game.ts:3927-3939; MenuUI.ts:779-786; TouchMobileControls.ts:73-90。
- **P1 Esc 语义五连裂**：单层面板=关面板；菜单子页/书架子册=跳级全关（与 ✕ 退一层割裂，BookshelfUI.ts:145-153; MenuUI.ts:303-306）；对话/遭遇=死键不可暂停（GameStateController.ts:161,235）；过场=无确认立即整段跳过（CutsceneManager.ts:553-556,679-687）；小游戏=退出。"后退一层"这条商业基本约定只在单层注册面板成立。
- **P1 对话中 backlog 不可开**：最需要回看上一句的时刻按 L 无反应（Game.ts:3930 无 alwaysOpenable）。
- **P1 面板全互斥无横向切换**：开着任一面板按其它面板键被静默吞、无提示音（GameStateController.ts:161-162,200-208）；唯一横跳 bookshelf→rules 还是单向的（Game.ts:1121-1124）。
- **P1 MenuUI + InventoryUI 纯鼠标**，与 11 个已接 UIFocus 的面板形成断档；全库零手柄支持。
- **P1 规矩本与用规矩零衔接**，且 HUD 亮 [G] 时按 G 可静默无反应（ZoneSystem.ts:275-282; RuleUseUI.ts:96-97,130; GameStateController.ts:173-176）。
- P2 handleEscape 以注册序倒序当"最上层"（GameStateController.ts:220,228）；触屏「铺子」死 chip（TouchMobileControls.ts:81; ShopUI.ts:121）；BookReader 无上一章/下一章。

### clarity（信息层级/文字重点）

- **P1 灰域 14 档无语义映射**：0x6b6355~0xccbbaa 窄带里挤了约 14 档近邻暖灰（含两对同值双名），相邻档亮度差常 <10%，颜色作为次要层级载体实际失效——字号七档有纪律、颜色零纪律，是"文字没有重点"的**令牌层根因**（UITheme.ts:53-146,115/138,116/139）。
- **P1 五本册子正文单样式零层级**：数据层语义字段很全（印象/例/来源/note/集齐评语），薄壳拼成纯字符串后一种字号一种颜色渲染（ArchiveBookView.ts:450-456 + 五壳 buildDetail）——"文字没有重点"的**最实锤落点**；数据里现成的 [c:] 色板通道薄壳一个都没用。
- **P1 QuestPanel 文案与交互打架**："‖ 搁置·点击追踪"是 eventMode='none' 的死文字（strings.json:150; QuestPanelUI.ts:877-892）；列表灰简述与右栏正文同字段，36% 行宽零新信息（:308-309）。
- **P1 存档槽单行纯文本**：场景名/天数/日期/时长同字号同色挤一行，无缩略图（MenuUI.ts:583-592）。
- **P1 地图零图例**：六种视觉语义（当前/可去/hint 锁/???/任务虚环/路线弧）无一处解释（MapUI.ts:501-655）。
- **P1 键帽提示不分平台**：[G]/[E]/按住[空格] 在触屏原样显示，指向不存在的键盘（HUD.ts:213,517-541）。
- P2 空态语汇不统一且皆无引导（Inventory 无文案/Quest/Rules 角落一句暗灰，三块 84% 屏宽面板空时近乎白板）；页签丢计数（QuestPanelUI.ts:247-253）；notification 类型色直接当正文 fill；InspectBox 无对象名。

### layout（排版/图片能力）

- **P0 组件层无任何布局原语**：无栈/网格/分栏/页签/流式容器，30+ 面板全部手写 cy 累加与手算栏宽，页签这个商业标配全项目没有组件——"表现逻辑乱、各面板乱搭"的第一根因（ArchiveBookView.ts:279-309; QuestPanelUI.ts:552-555; UIWindow.ts:150-152）。
- **P1 图文排版天花板**：RichContent 仅块级竖排+左贴 ≤200px 图，无对齐/图注/环绕/行内图/文档语义标记（RichContent.ts:7,75-134,106-111）——详见⑤。
- **P1 顶中 100px 带挤四通道无仲裁**：场景名 y=10/引导 y=44/toast y=50 起/横幅 y=96，toast≥1 条即盖引导、≥2 条即压横幅，重叠是必然非偶发（HUD.ts:229; GuidanceLayerUI.ts:28; NotificationUI.ts:57; QuestBannerUI.ts:40）。

## ⑤ 收集册图文排版能力专章

### 现状真实上限（全族唯一通道 RichContent.ts:75-134）

**有**：`[img:短名]` 把正文切成文/图交替段，纯竖向顺排（段距硬编 10px）；图等比缩至 min(栏宽, 200px 高)且两个调用方都不传 imageMaxHeight——**全站档案图硬上限 200px 高、x 恒 0 贴左**；文本段支持 [c:] 换色（仅 fill）；缺图占位素净不露路径、异步现装、ArchiveManager 空闲池化预热（这三点是加分项）。

**没有**（对标逆转证物册"图+名+说明卡片"、山河旅探档案插画版式）：
- 图：无居中/右置、无文字绕排、无行内小图、无图注、无并排/画廊、无点击放大、无与木框皮肤衔接的图片边框、无整页/卷首插画（BookReader 的 illustration 被拼成 [img:] 前缀恒在页首，BookReaderUI.ts:540-543）；
- 文：正文流内无小节标题/引文/列表/分隔线语义——标记语言只有 [img:] 和 [c:] 两个，"小节标题+引文+插图+注"这种版式**数据侧根本无法表达**；parseSegments 还 trim 掉作者用空行做的节奏（RichContent.ts:65-71）；
- 皮肤：SKINS 16 种全是暗底，无亮底"纸页"材质（PanelSkin.ts:76-97）——米白纸页+墨字+插图的商业档案观感第一步就撞墙，MapUI 被迫自建 11 色羊皮纸色板证明需求真实而令牌层没接住（MapUI.ts:44-55）；
- 数据：CharacterEntry 无任何图片字段（types.ts:1916-1924），人物簿天生无头像位；按语通道半承诺（ArchiveManager 预热扫 [img:] 而渲染端不解析，ArchiveManager.ts:237-239 vs BookReaderUI.ts:561-577）。

### 结论与缺口清单

现状是"能塞图的纯文本"，离"图片内容+自由排版"差**一个小型文档布局器**：
1. RichContent 从"分段渲染器"升级为**块级+行内两层的版式引擎**（块类型：标题/正文/引文/图/图注/分隔；行内：着色/强调/行内图/可点 span）；
2. **纸页皮肤**（亮底材质）进 SKINS + 配套墨字色板进 UITheme 子色板机制；
3. 数据形状补齐：CharacterEntry 加 portrait 字段、BookPage 支持整页插画位、图注语法；
4. UI 功能图标库（箭头/锁/新标等，当前 16 枚全是物件剪影，UIIcons.ts:14-19）。

改造面是**收敛的**：1 个文件 + 2 个调用方（ArchiveBookView/BookReaderUI），[img:] 语法已在内容侧铺开、通道选对了。且这次改造与诉求三共用（见⑥）。

## ⑥ "标记 → 可点击 → 采集线索"设计方向草案

### 现状距离（四桶独立评估收敛后的共识）

**已白捡的（约六成地基）**：[c:id]…[/c] 标记有完整 tokenizer/校验器/打字机安全截断（textStyle.ts:116-127,183-249,290-322）；色板已预留 clue 语义 id（textStyle.ts:33 #8fae72）；全 UI 文本经唯一工厂 createStyledText（130+ 调用点），原始标记文本 WeakMap 全程可取——加交互层只动一个 seam；resolve 链路保证标记从 JSON 活到渲染帧；指针消费机制与 UIFocus 为"点词条不误触推进对话""键盘选词条"提供现成地基；采集落库骨架现成（FlagStore+ConditionExpr+ArchiveManager 声明式解锁收敛，ArchiveManager.ts:489-537）；Notification 可低成本扩 clue 类型回执。

**为零的（三层缺口）**：① 标记语法无载荷——[c:clue] 表达不了"哪一条线索"，需带 id 的第三层标记；② span 几何与命中层——单 Pixi Text 不暴露字形几何，全项目无任何词级定位代码；③ 线索数据面——无 ClueManager/采集动作/存档字段/线索册（grep 全 src 仅色板与注释命中）。**这属于"缺一层"而非"缺一切"，总量 = 一个中型系统而非重构。**

**已知地雷**：正文同时含裸 `<` 与色标记时整句无声降级纯文本（textStyle.ts:155-171）——标记承载线索语义后这条降级会让线索**无声消失**，动工前必须改为转义保留或校验器挡死。

### 方案 A（推荐）：run 级富文本组件 + 静态册面试点，与图文排版捆绑同一次改造

- **交互形态**：档案册/成书正文里的线索词呈 clue 苔绿色，hover 转亮+下划线短琥珀线（沿用"点亮一档琥珀"定稿语汇），点击→采集动画（词条闪金）→Notification clue 类型回执"已录线索：xxx"；已采词转暗金常驻。键盘：词条注册进 UIFocus 焦点项。
- **数据形状**：新标记层 `[clue:id]…[/clue]`（与 [tag:] 引用层、[c:] 样式层并列第三层，扩 textStyle 同一 tokenize 家族）；线索注册表 clues.json（id→title/desc/入哪本册/关联条目）；点击→set flag `clue_<id>`→现有条件系统即刻消费（解锁档案条目/对话分支）。
- **渲染落点**：RichContent 升级为 run 级布局（tokenize 切 run→逐 run Text 中文逐字断行→可点 run 挂 hitArea+markPointerConsumed+注册 UIFocus）——**可点 span 命中矩形是图文排版引擎同一次改造的副产品**，两笔投资合一。
- **系统落点**：ClueManager（或并入 ArchiveManager）+ ActionRegistry 采集动作 + IClueDataProvider 照 quest/rules 的 provider 范式喂 UI；线索册直接复用 ArchiveBookView。
- **先落静态正文面**（ArchiveBookView 右栏/BookReader：无打字机、无点击推进冲突），对话框二阶段。
- 优点：一次投资吃两个诉求；架构分层干净；无引擎级障碍。代价：run 级断行器是真实工程量（中文逐字断行 breakWords 已是全站现状口径，难度可控）。

### 方案 B：单 Text + CanvasTextMetrics 命中层（对话框二阶段的过渡技术）

- 利用关键幸运：tagStyles 只改 fill 不改字形度量（textStyle.ts:102-107），带标记文本换行/字位与纯文本逐像素一致——可用 CanvasTextMetrics（DialogueLogUI.ts:302-308 已示范同口径量高）反推每个标记 span 的行内矩形，在现有单 Text 上叠透明命中层，**无需换渲染器**。
- 适合打字机场景（DialogueUI/EncounterUI）：不动现有 reveal 逻辑，命中区按 displayedChars ≥ span 末端门控出现；随 wordWrapWidth/resize/立绘 inset 重算（relayout/onResize 是现成时机）。
- 局限：hover 只能叠加高亮框做不了字内样式变化；每处调用要自己接重算时机；不解决图文排版。**定位为 A 落地前/对话面的补充路线，不做主干。**

### 方案 C：HTML overlay 混合（不推荐）

DOM 富文本浮层排版免费、可点免费，但破坏 Pixi 全画布输入统一性（markPointerConsumed 体系失效面扩大），且触屏 CSS 已证明平行皮肤必漂（touch-mobile-controls.css 手抄配色的教训）——与定稿的皮肤唯一入口纪律冲突，仅在原型验证期可用。

### 推荐与前置

**A 为主干，B 为对话面二阶段过渡，C 弃。** 三条前置：① 裸 `<` 降级地雷先挡死；② 输入路由/焦点栈地基先补（词条热区在多浮层下的按键归属，ActionChoiceUI.ts:245-287 已自注"地基缺口"）；③ 线索采集**会改玩法语义**，按项目流程先改 docs/玩法功能需求清单.md 对齐再动实现。
