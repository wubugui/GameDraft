# 预览页 rAF 节流 × dt 钳制 = 时间维度断言被放大约 7 倍

- **现象**：给 NPC 注入碰撞后验证"走不到就放弃"的 1.0 秒兜底，在预览页里实测要
  **15 秒**墙钟才触发。中途探针显示计时器每 700ms 只涨 0.1（应涨 0.7），一度看着像
  兜底逻辑写错了。
- **根因**：预览 pane 的 rAF 被节流到约 1~2 fps，而 `Game.mainTick` 的
  `dt = Math.min((now - lastTime) / 1000, 0.1)` **把每帧 dt 钳在 0.1 秒**。于是节流下
  "游戏内累计时间"只按 0.1/帧 前进 —— 1 秒的游戏内阈值需要 10 个节流帧 ≈ 7~15 秒墙钟。
  真机 60fps 下该阈值仍是准确的 1.0 秒。
- **影响**：凡是**按游戏内时长**判定的运行时逻辑（超时、冷却、兜底放弃、待机节目间隔、
  延迟事件），在预览页做真机验证时都会被拉长约 7 倍，且拉长倍数随节流程度浮动。
  照墙钟设等待时间很容易误判成"逻辑没生效"而去改本来正确的代码。

**对策**：验时间维度的逻辑，断言**最终状态**（封口了没 / 标志位对不对 / 告警发了没），
用轮询等到发生为止，**不要**按墙钟设固定 sleep 再断言；要读进度就读游戏内累计量
（如本次的 `stalledSeconds`），不要读 `performance.now()` 的差值。

现有 [runtime-command-channel](../../runtime/recipes/runtime-command-channel.md) 已记
"隐藏 pane 下轮询被节流到 ~1/分钟、命令 30s TTL 先到期"，但那条讲的是**命令通道**；
这条是**游戏内时钟**同源的另一面，建议一并收进该配方的「坑」。
