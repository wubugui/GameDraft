## 一句话

**原画就是辐射缓存。** 在伪世界里对它做一次 final gather，积出的就是这张画自己的
辐照度 `E`；天穹遮蔽是同一趟积分的另一个投影。不需要拟合任何照明系数。

## 为什么不拟合（这条是本卡存在的主要理由）

2026-08-22 走过另一条路：把原画的照明拟合成

```
E_est = flat + sky·T₀ + ao·AO + src·S_local        四系数在单纯形上网格搜索
```

判据是"除干净之后残留不该再与任何基相关"（分层解耦）。**这条路错在方向上**：

- `S_local` 是"从原画里检测出的亮斑 + 1/r² splat"，它对**任何**图都近乎自解释，
  是个循环基。于是在搜索里它永远压过 `sky` —— 28 个场景里 **23 个天穹系数被压到 0**，
  连 `mountain_pass`（画里根本没有灯的山口）都拿到 0.75 的 `src` 权重，
  实际检出的"光源"是溪流的水面高光和被太阳照亮的岩面。
- **整套天空遮蔽因此等于没开**，而残留指标全程漂亮（0.06–0.23）。

> **分数低 ≠ 机制分对了。** 指标只说"模型能复现这张画"，不说"模型把光归给了正确的
> 机制"。查这类问题要看**系数落在哪**，不能只看残留。

试过给检测器加自发光闸（峰值 / 超额通量），能把假光源挡掉，但那是在给一个方向
错误的方法打补丁 —— 真正的问题是**不该拿原画去回归照明**。

## 现在怎么算

```
E(x) = ∫ L_in(x,ω)·max(N·ω,0) dω  ÷  ∫ max(N·ω,0) dω

L_in(x,ω) = HDR(原画) @ 命中点      射线在伪世界深度里打到表面
          = 天空辐射               射线逃逸
```

- **没有系数、没有判据、没有搜索**。
- **不需要检测画里的灯**：灶口的 HDR 辐射本来就高，附近地面在积分里自然被照亮。
- **天穹遮蔽顺带出**：同一趟 march 里"朝上且逃逸"的加权占比就是 `T_k`。分两趟算
  既慢又有分家的风险。为此 gather 的方向集**复用** `sky_directions()` 的那 96 个
  （加上它们的镜像组成全球面），解析锚点（无遮挡朝上 1.0 / 竖直 0.5）原封不动。

## 天穹遮蔽：存的是**传输**，不是可见度

这两个量差一个余弦因子，混起来看是 2026-08-23 那次"这天空 occlusion 看着非常奇怪"
的全部原因：

```
T₀(p) = cap₀(N) · V(p)          cap₀(N) = (1 + N·up)/2
```

- `T₀`（存在 `transport.png`，运行时消费的就是它）是**传输系数** ——
  `E_天光 = 天光强度 · T₀`，余弦**必须**在里面，这是对的。
- `cap₀` 是无遮挡时的传输，只由朝向决定，**有闭式**：`(1+N·up)/2`
  （朝上 1、竖直 0.5、朝下 0；四个通道都数值验算过）。
- `V = T₀ / cap₀` 才是"这一点看得见多少天"，与 `ao.png` 同口径。

实测 `cap₀` 中位 0.70、值域 0.15–1.0 —— 所以**直接看 `T₀` 看到的主要是法线明暗**：
桥洞底下和开阔水面一样亮，整张图读起来像一块打了顶光的橡皮泥。除掉 `cap₀`
之后拱洞才正确地黑下去。

- F2 第 4 档出的是 `V`（`sc3SkyVisibility`），第 5 档出的是当前天穹剖面下的真实传输。
- 烘焙预览同时出 `preview/transport_y0.png`（传输）与 `preview/sky_visibility.png`（可见度）。

⚠ **着色一律用 `sc3SkyTransfer`，`sc3SkyVisibility` 只给出图用。** 拿可见度去着色
= 把余弦项漏掉。

### 这套遮蔽的物理边界（重要，别当 bug 修）

伪世界是**单视角高度场**，所以"头顶有没有东西"只在画里画了的时候才存在：

- 户外画得出的遮挡是对的。bridge_underpass 实测拱洞内 `V` 掉到 0.2–0.4，
  开阔水面 ≈1.0。
- **室内画普遍没有屋顶**（45° 俯视，屋顶被作者切掉了）。teahouse 的 `V` 中位 0.61、
  梦_里屋 0.66、义庄 0.70 —— 对**重建出来的那个开顶盒子**而言这是正确答案，
  屋顶根本不在数据里。
- 后果：给室内场景调高 `sky.intensity` 会像掀了屋顶一样整屋提亮。
  想压暗室内用 `ambient` + AO，或者把屋顶画进深度图。
- `E` 不受影响：室内逃逸射线取到的"天空辐射"是 `sky_mask`（视深最远 8%）
  选中的那面远墙，本来就暗。

唯一的建模假设：8-bit 原画的高光被压过，假设它按 Reinhard `y = x/(1+x)` 压过并
逆映射展开回 HDR（`HDR_MAX = 200`）。不展开的话灶口和白墙线性化后都贴在 1.0 附近，
灶口照不亮任何东西。

## 场景法线是**世界法线，全值域**（和角色那套刻意不同）

`lighting3/normal.png` 三通道同一条 `n*0.5+0.5`，解码统一 `*2−1`。

角色法线贴图是**视空间**的，可见面的法线必然朝相机、z 恒为负，所以它存 `|z|`、
解码 `-max(b, 0.05)` —— 无损。世界法线不是这样：实测 28 个场景 `n.z > 0` 的像素
占 **10.6%–39.8%**（最高 +0.74），`|z|` 那套**根本表达不了**。

⚠ 这个坑踩过两次，两次都是"照抄了另一条路径的约定"：

| 日期 | 症状 | 实测偏差 |
|---|---|---|
| 2026-08-20 | 场景 pass 三通道一起 `*2−1` 再 `-abs(z)`（配 v2 的 `\|z\|` 编码） | 中位偏 20.4° |
| 2026-08-23 | v3 改成全值域编码，场景 pass 还留着 `-max(b,0.05)` | 中位偏 **23°–33°**，25%–57% 的像素偏超 30° |

第二次尤其阴：默认 `gi = 1` 时画面只走 `base·E + emissive`，**根本不过法线**，
所以画面完全正常、tsc 与全部单测全绿；只有一重打光，每盏灯的 N·L 才集体歪掉。
机械契约在 `src/rendering/lighting/normalEncoding.test.ts`（四处代码一起锁）。

## 反射 / 自发光的拆分是**定义**

表面反射不可能超过它收到的光，超出的按定义是自发光：

```
base     = min(I / E, 1)
emissive = max(I − base·E, 0)
恒等:  base·E + emissive ≡ I
```

烘焙期把这条做成断言（全量实测往返 p99 ≤ 1.1/255，门槛 2.0）。三个后果：

1. 画里的灯（灶口、灯笼、天）自动落进 `emissive`，运行时原样加回、不乘任何 `E`；
2. `base ∈ [0,1]` 有了**物理上界**，编码才有个能钉住的锚点（不拆的话 `I/E`
   在灯上顶到 78，只能拿 p99.9 当 scale，中位就剩 4 个量化档 —— 实测往返 27.9/255）；
3. 天整个归 `emissive`（天不反射光，它就是光）。

`emissive` 由**解码回来的** `base` 反推，所以连量化误差都被吸收 —— 恒等是精确的。

## 「基底」不是 albedo

`base := I_原画 / E` 是比例式 `I_out = I_原画 × E_目标 / E` 里被提出来的中间因子。
数值上落在反射率量级（因为 `E` 是真辐照度），但它**不是反解出的材质**。
叫它 albedo 会带来"我们反演出了物理量"的错误预期。

## 默认状态：`gi = 1` ⇒ 画面精确等于原画

`E` 与 `emissive` 都随包发出。运行时：

```
输出 = base · (gi·E + 天光·T + 环境·AO + 日月 + 灯) + emissive·emissiveScale
```

`gi = 1`、天光/环境 = 0 时化简为 `base·E + emissive ≡ 原画`。

⚠ 这与 v2 的 `placeholder` **不是一回事**（那个已删除）。`placeholder` 是"整条链
绕过去"的开关，而它的恒等**只对背景成立** —— 角色被整个挡在门外，27 个场景里
摆多少灯角色都零响应。这里 `gi` 是光照方程里一个有物理含义的项，**角色从同一份
GI 网格里按自己的世界位置和法线查值**，走的是完全相同的那条链。

重打光 = 把 `gi` 调低 + 把天光/灯加上去。这是一条**连续**的路。

## 角色为什么必须吃烘焙 GI

`sky_sh_grid.bin` 现在是 8 通道：4 个天穹纬向传输 + 1 个局部 AO + **3 个 GI 的 RGB**
（同一个 gather，起点换成网格点，SH-L1 表示）。

`charGi` 缺省 1。调到 0 之前先确认场景有别的光 —— 未重打光的场景 `sky`/`lights`
都是 0，此时角色会**全黑**，正是 `placeholder` 造成过的那个症状。

## 编码：两条曲线，别混

| 载荷 | 编码 | 为什么 |
|---|---|---|
| `irradiance.png`、网格 GI 幅度 | **对数**（中位居中，±8 档） | 动态范围 400 倍（烛火旁 vs 暗角），相对精度需要全程恒定 |
| `base.png` | **对数**（一侧对齐：`scale = 2^-8`），**字节 0 = 精确的 0** | 同上，外加下面两条 |
| `emissive.png` | `from_hdr` = `x/(1+x)` 再 sRGB8，**无 scale** | 大部分像素恰好是 0，log 表达不了 0 |

三条踩过的坑，每条都对应一个**指标不报、画面变样**的缺陷：

1. **对数编码的 `scale` 取中位不是 p99.9。** 取 p99.9 会把典型值推到编码量程底部
   —— 往返 p99 从 0.56 炸到 40/255。
2. **`base` 不能用 sRGB8。** sRGB 暗端那段线性趾部的绝对步长恒为 `3.0e-4`，
   而暗物体逆光剪影的 base 实测就在 3e-4 —— **一档 100% 相对误差**。乘上巨大的
   `E`（梦_醒来土路 中位 999）之后是肉眼可见的偏差：往返 p99 22.2/255，
   误差 99 分位像素的 base 中位恰好是 3e-4。
3. **字节 0 必须表示精确的 0，且 `base_q ≤ base` 要有保证。** 真值低于编码下限的
   近黑像素被抬到下限之后 `base·E` 超过原画，`emissive = max(原画 − base·E, 0)`
   只能钳成 0 —— 恒等式在那里破掉，本该全黑的地方发灰。修法是字节 0 特判 +
   溢出时把字节下调一档（只动真的超了的像素：一律向下取整会让每个像素少 4.35%
   的反射能量，那部分被重新归类成自发光就不再参与重打光了）。

`from_hdr` + sRGB8 的甜区只有 0.1–3（相对误差 <2%），到 10 就 5%、30 就 9%、
200 直接截断。给它配 scale 也救不了 400 倍的动态范围 —— 那是**换编码**的理由，
不是调参的理由。

## 升采样必须在**编码域**做

GPU 的线性过滤作用在纹理字节上，之后 shader 才解码。对数编码下
「先解码再插值」≠「先插值再解码」（后者是线性域的**几何平均**）。

⚠ 烘焙若按前者算 `E`，据此反推的 `base` 就与运行时实际拿到的 `E` 对不上，
而**往返指标测不出来** —— 它用的是烘焙自己那份 `E`。这是一个指标全绿、
画面偏一点点的盲点。所以 `resize_encoded` 逐字照抄 GPU 的顺序。

## 摆灯的尺度**逐场景不同**，而且不能归一

`E` 的中位跨 28 个场景差 **25000 倍**（城隍庙夜 0.04 ↔ 梦_醒来土路 1041），
因为 `to_hdr` 对亮画的展开是指数级的。同一个 `intensity` 在不同场景里效果天差地别。

⚠ **不能把 `E` 归一到中位 1**：`base ≤ 1` 这条物理钳位（反射不超过入射）就绑在
`E` 的绝对值上，缩 `E` 会让 `base` 全部撞顶、整张图退化成自发光。

既然改不了，就把它摆到台面上：F2 第一行显示**本场景光尺度**
（= `runtime_fit.sky + runtime_fit.ambient`，也就是"用解析天光+环境完全替换掉
烘焙 GI 时那两个系数之和"）。摆灯从这个量级起步。

## 显示变换被迫换基线（唯一波及美术参数的地方）

v3 的 pass 输出的是**真 HDR 辐射**（`to_hdr` 把原画的高光展开回去了，量程到 200），
不再是 v2 那种落在 [0,1] 的「原画 × 比值」。而 28 个场景里 **27 个写的是
`display.tonemap: 'none'`** —— 那会让画面整片过曝到全白。

`reinhard` 恰好就是 `x/(1+x)`，也就是 `from_hdr` 的正向。于是

```
ev = 0 + reinhard  ⇒  linearToSrgb(from_hdr(base·E + emissive))  ⇒  精确还原原画
```

所以迁移器把 `display.ev` / `display.tonemap` 换成 `0 / reinhard`。
**对那 27 个 `none/0` 的场景，画面与迁移前完全一样** —— 不是"差不多"，是恒等。

唯一真会变的是**雾津街头**（`filmic` + `ev 3.32`）。那个 ev 本来就是在补 v2 管线
自身的尺度（见 [per-scene-exposure](2026-08-21-per-scene-exposure.md)），
新管线里原画本来就精确还原，补偿不再需要。作者要另一种观感就从这个基线上重调。

`whiteKelvin` / `contrast` / `saturation` / `lift` 都在 tonemap **之后**生效，
语义没变，迁移器原样保留。

## `renderRaw` 装饰实体：只吃比值，不做基底反解

`renderRaw` 的实体（从背景抠出、贴回原位做循环动画的装饰，例如茶馆的五个
`fx_patron_*` 坐客）历来**不附加任何逐 entity 光照** —— 它们的像素取自已经烤好
光照的背景，叠一层角色着色会与背景色调不符、露出方框接缝。

但「不附加角色着色」不等于「不受重打光影响」。补丁的像素是原画在那个位置的
出射辐射，所以它该走的正是背景走的那条变换：

```
I_out = I_补丁 × E_目标 / E
```

而 `E_目标/E` 无需重算光照 —— 场景 pass 的输出里就有：

```
lit  = base·E_目标 + emissive          ← pass 的 RT
比值 = (lit − emissive) / (base·E)      = E_目标/E
```

★ **`gi = 1` 时分子分母恒等 ⇒ 比值恒为 1 ⇒ 逐像素不变。** 这条是这条路径能上线的
前提：现状已经是精确的，任何改动都不许把它弄丢。实现见 `RawPatchRelightFilter`。

真机验过的两条：
- `gi = 1` 时开关该滤镜，五个补丁的画面**差值逐项为 0**；
- `gi` 1.0→0.15 时背景 42.6→16.1、补丁 56.3→20.0 跟着走（不挂滤镜的话补丁停在
  55.4，会明显浮起来）。

⚠ 两个坑，都踩过：
1. **比值只能取反射那一份**（`lit − emissive`）。用整像素的 `lit/原画` 会把背景
   那个像素的自发光（灶口、灯笼）也算进去，凭空提亮补丁 —— 补丁是反射体。
2. **三张原生图必须取同一个纹素**，不能各自做线性过滤。`lit` 是 pass 在某个纹素
   上算出的一个值，而 `base`/`emissive` 若被过滤拿到的是邻居的混合，
   `blend(f(x)) ≠ f(blend(x))` —— 实测那样让补丁在 `gi = 1` 时也亮 0.2%–4.7%。

## 机械契约

`src/rendering/lighting/gatherPipeline.test.ts` 钉住了：拟合那一套的定义不许回来、
入射辐射只有"命中点的画"与"天空"两种来源、E 与 T 同一趟 march、gather 的上半球
方向与 `sky_directions()` 逐位相同、拆分恒等式的两条式子、三种编码与 shader 侧解码
逐字对齐、`gi`/`charGi` 两处缺省都是 1、显示变换的 reinhard 基线、
以及升采样必须在编码域做。

产物与运行时接口的一致性另有一条：`tools/scene_relight/tests/test_meta_contract.py`
拿**真实烘出来的 meta.json** 跟 `LightingGeometryMeta` 逐键对 —— 「类型声明不是数据
契约」这个坑在 `scale` 和 `grid`/`band`/`depth_range` 上各踩过一次，两次都是
`tsc` 全绿而真机出事。
